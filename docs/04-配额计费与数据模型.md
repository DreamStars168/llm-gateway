# 04 配额、计费与数据模型

> 目标：并发下不超卖、流式也能准、账能对上、查得快。
> 核心：**两阶段提交（预扣 → 结算）+ 单次 Lua 原子操作 + 异步落库**。

---

## 1. 计费模型

### 1.1 计费维度

| 维度 | 说明 | 来源 |
|---|---|---|
| 输入 token | prompt tokens | 上游 usage 优先，缺失则 jtokkit 估算 |
| 输出 token | completion tokens | 同上 |
| 缓存写 token | Anthropic `cache_creation_input_tokens` | 上游 usage |
| 缓存读 token | Anthropic `cache_read_input_tokens` / OpenAI `cached_tokens` | 上游 usage |
| 推理 token | `reasoning_tokens`（通常已含在 output 内） | 上游 usage |
| 请求次数 | 用于"按次套餐" | 网关计数 |
| 图片/音频 | 按张/按秒 | 上游返回或按规则表 |

### 1.2 定价结构（分级定价）

```yaml
# price_rule 一条记录
virtual_model: claude-sonnet-4
currency: USD
tiers:                          # 命中第一个满足条件的档
  - when: { input_tokens_lte: 200000 }
    input: 3.0                  # 每百万 token
    output: 15.0
    cache_write: 3.75
    cache_read: 0.30
  - when: { input_tokens_gt: 200000 }   # 长上下文溢价
    input: 6.0
    output: 22.5
    cache_write: 7.5
    cache_read: 0.60
channel_multiplier:             # 渠道倍率（不同上游成本不同）
  ch-openai-main: 1.0
  ch-deepseek: 0.15
group_discount:                 # 分组折扣
  vip: 0.9
```

- 定价表本地缓存（Caffeine，按 `virtualModel + channelId`），变更走配置版本失效。
- 金额统一用 `BigDecimal`，DB 用 `DECIMAL(18,8)`，**禁止 double**。
- 内部记账单位：`micro-USD`（long，1 USD = 1_000_000），避免小数累积误差；对外展示再转美元。

### 1.3 成本计算

```java
BigDecimal cost = input.mul(p.inputRate)
    .add(output.mul(p.outputRate))
    .add(cacheWrite.mul(p.cacheWriteRate))
    .add(cacheRead.mul(p.cacheReadRate))
    .divide(ONE_MILLION, 8, RoundingMode.HALF_UP)
    .multiply(channelMultiplier)
    .multiply(groupDiscount);
```

四舍五入到 8 位小数；单次请求成本 < 0.00000001 USD 时记 0（避免海量微账单）。

## 2. 两阶段配额

### 2.1 为什么必须两阶段

流式请求的最终 token 数在响应结束才知道。如果只在结束时扣：
- 并发 1000 个请求，每个预估 2000 token，余额只够 500 个 → 全部放行 → 结束时一半扣失败 → **超卖**。

如果按预估一次性扣且不修正：
- 预估偏高 → 用户额度被浪费；预估偏低 → 仍然超卖。

### 2.2 状态机

```
   ┌──────────┐   reserve(est)    ┌───────────┐   settle(actual)   ┌───────────┐
   │  IDLE    │──────────────────▶│ RESERVED  │───────────────────▶│ SETTLED   │
   └──────────┘                   └───────────┘                    └───────────┘
                                        │
                                        │ release（上游失败/客户端取消）
                                        ▼
                                  ┌───────────┐
                                  │ RELEASED  │
                                  └───────────┘
```

- `reservationId = requestId`（幂等键）。
- 预扣额度：`est = min(max_tokens, modelDefault) * outputRate + estimatedInputTokens * inputRate`，再乘 1.2 安全系数。
- 结算：`delta = actual - est`，正数补扣（可能不足，记欠款）、负数退回。
- 超时未结算（>10min）：定时任务扫描 `quota_reservation` 表，按预扣额结转为实际消耗并告警。

### 2.3 Redis 数据结构

```
quota:{tenantId}:balance          STRING  (micro-USD，可为负=欠款)
quota:{tenantId}:reserved         STRING  (当前预扣总额)
quota:{keyId}:used:{yyyymmdd}     STRING  (当日已用，EXPIRE 2d)
quota:{tenantId}:rpm:{minute}     STRING  (分钟请求数)
reservation:{requestId}           HASH    {tenant, key, amount, status, ts}
```

- 余额校验：`balance - reserved >= amount` 才允许预扣。`reserved` 的存在保证并发下不会"看到同一个余额都放行"。

### 2.4 预扣 Lua（单脚本、单 RTT、原子）

```lua
-- KEYS[1] = quota:{tenant}:balance
-- KEYS[2] = quota:{tenant}:reserved
-- KEYS[3] = reservation:{requestId}
-- ARGV[1] = amount(micro), ARGV[2] = ttlSec, ARGV[3] = tenantId, ARGV[4] = keyId
if redis.call('EXISTS', KEYS[3]) == 1 then
  return 2                                   -- 幂等：已预扣，直接成功
end
local bal = tonumber(redis.call('GET', KEYS[1]) or '0')
local res = tonumber(redis.call('GET', KEYS[2]) or '0')
local amt = tonumber(ARGV[1])
if bal - res < amt then
  return 0                                   -- 余额不足
end
redis.call('INCRBY', KEYS[2], amt)
redis.call('HSET', KEYS[3], 'amount', amt, 'status', 'RESERVED',
           'tenant', ARGV[3], 'key', ARGV[4], 'ts', ARGV[5])
redis.call('EXPIRE', KEYS[3], ARGV[2])
return 1
```

> 只有 1 次 RTT，脚本内无网络调用，Redis 单线程保证原子性。`EXISTS` 幂等使重试安全。

### 2.5 结算 Lua

```lua
-- KEYS[1]=balance, KEYS[2]=reserved, KEYS[3]=reservation
-- ARGV[1]=actual(micro), ARGV[2]=requestId
local st = redis.call('HGET', KEYS[3], 'status')
if st == 'SETTLED' then return 2 end          -- 幂等
if st == false then return 3 end              -- 无预扣记录（降级场景），直接扣 actual
local est = tonumber(redis.call('HGET', KEYS[3], 'amount'))
redis.call('INCRBY', KEYS[2], -est)
redis.call('INCRBY', KEYS[1], -tonumber(ARGV[1]))
redis.call('HSET', KEYS[3], 'status', 'SETTLED', 'actual', ARGV[1])
return 1
```

- 允许 `balance` 变负（欠款），下一次预扣自然失败 → 相当于"软停机"。
- `reserved` 在结算时必须减掉 `est`，否则会永久泄漏。

### 2.6 释放 Lua（失败/取消）

```lua
local est = tonumber(redis.call('HGET', KEYS[3], 'amount') or '0')
redis.call('INCRBY', KEYS[2], -est)
redis.call('HSET', KEYS[3], 'status', 'RELEASED')
return 1
```

> 若已收到部分输出（流中断），不要 `release`，改走 `settle` 并传 `estimated=true` 的部分用量。

### 2.7 Redis 超时与降级

预扣是请求关键路径上唯一的同步 Redis 调用，必须设上限（默认 `300ms`，对应 03 文档超时分层）。超时后的行为按租户配置：

| 模式 | 行为 | 适用 |
|---|---|---|
| `FAIL_OPEN`（内部租户默认） | 放行请求，内存记一笔"待补扣"；请求结束照常发 `UsageEvent`，由消费者按实际用量补扣 | 可用性优先 |
| `FAIL_CLOSED`（付费租户默认） | 返回 503 `quota_unavailable` | 资金安全优先 |
| `LOCAL_QUOTA`（降级档） | 用本地 Caffeine 维护余额副本做近似判断，恢复后以 Redis 为准对账 | 短时抖动 |

> `FAIL_OPEN` 不等于"白送"。`UsageEvent` 带 `degraded=true`，消费者发现 Redis 无预扣记录时走 2.5 结算脚本返回 3 的分支（直接按实际扣减），保证账最终能对上。
> 三档都需在压测中验证：向 Redis 注入 500ms 延迟时，`FAIL_CLOSED` 应稳定返回 503 且不拖垮其他请求（超时即放弃，不排队）。

## 3. 用量采集

### 3.1 数据来源优先级

1. 上游 `usage` 字段（最准）
2. 上游 `x-ratelimit-*` 头（仅部分厂商）
3. 网关本地估算（`jtokkit`，按模型选择 tokenizer；未知模型用 `o200k_base` 近似）

估算必须打标：`usage_source = UPSTREAM | ESTIMATED`，并在对账时区分。

### 3.2 采集点

```
RelayPipeline
   ├─ 非流式：解析响应体 usage（同协议透传时也要解析一次，因为要计费）
   ├─ 流式：TailUsageSniffer 扫尾帧
   └─ 未拿到：TokenEstimator 估算（prompt 用 IR，completion 累计 delta 字符数）
```

### 3.3 异步落库链路

```
RelayPipeline ──▶ UsageEvent ──▶ RabbitMQ(exchange=usage, routing=usage.record)
                                    │
                                    ├─▶ 队列 usage.persist  ──▶ 批量 INSERT relay_log（500 条/批 或 1s）
                                    ├─▶ 队列 usage.aggregate ─▶ 累加 tenant_daily_stat（UPSERT）
                                    └─▶ 队列 usage.billing   ─▶ 生成 bill_item、触发额度告警
```

- Producer 端：`publisher-confirm` + 本地 `ConcurrentLinkedQueue` 兜底；confirm 失败重投，超过 3 次落 `usage_outbox` 表。
- Consumer：手动 ack，处理失败 `basicNack(requeue=false)` → 进 `usage.dlq`，由补偿任务重放。
- 批量写：`INSERT ... ON DUPLICATE KEY UPDATE`，按 `request_id` 幂等。

### 3.4 为什么用 MQ 而不是直接写库

| 方案 | P99 影响 | 数据安全 | 复杂度 |
|---|---|---|---|
| 同步写 MySQL | 写库 RT 直接叠加到请求尾 | 强 | 低 |
| 异步线程池 | 不叠加，但进程崩溃丢数据 | 弱 | 低 |
| **MQ + outbox** | 不叠加 | 较强（至少一次） | 中 |

简历里"RabbitMQ 异步削峰落库"要能说清：**削的是写库峰值，保的是请求尾延迟**；配合幂等消费实现"至少一次 + 去重"。

### 4.3 索引原则

- 所有列表查询必须带时间范围（强制 `created_at >= ?`），否则走分区裁剪失败。
- `relay_log` 只存元数据，**不存请求/响应体**；需要留存的走对象存储并记 `payload_uri`。
- 大字段（`route_trace`、`extra`）用 JSON，不建索引，只做展示。
- 冷热分离：`relay_log` 保留 30 天，之后归档到 ClickHouse / 对象存储（第二期）。

### 4.4 分库分表预案

单表 `relay_log` 超过 5000 万行时的演进路径：
1. 按月分区（首选，改造成本最低）
2. 按 `tenant_id` 哈希分 16 库（ShardingSphere），聚合查询走汇总表
3. 明细迁 ClickHouse，MySQL 只留 `usage_daily`

## 5. 对账

| 对账项 | 频率 | 逻辑 |
|---|---|---|
| 预扣 vs 结算 | 每小时 | 扫 `quota_reservation` 中 `RESERVED` 且超 10min 的记录，按预扣额结算并告警 |
| 网关用量 vs 上游账单 | 每日 | 拉取上游 usage API（支持的厂商），比对差异 > 5% 告警 |
| `relay_log` vs `usage_daily` | 每日 | 重算聚合，覆盖写入（幂等） |
| Key 余额 vs 预扣总额 | 每小时 | `balance` 与 `reserved` 的一致性校验，异常自动修复 |

## 6. 并发扣减测试方案（简历指标的证据）

### 6.1 测试设计

```
初始余额 = 100.00 USD
单次请求预扣 = 1.00 USD
并发线程 = 1000（JMeter / Gatling）
期望：恰好 100 个请求成功，900 个返回 402 insufficient_quota
```

### 6.2 断言

- `success_count == 100`（严格相等，不允许 99 或 101）
- `balance == 0`，`reserved == 0`（结算后无泄漏）
- 无 Redis 报错，`quota_reserve_duration P99 < 2ms`

### 6.3 反例验证（证明设计必要性）

去掉 `reserved` 只校验 `balance`，同样测试应出现 `success_count > 100`（超卖）。把该对比写进测试报告，是方案有效性的直接证据。

### 6.4 边界用例

| 用例 | 期望 |
|---|---|
| 同一 requestId 重试 3 次 | 只扣一次（幂等） |
| 预扣成功但上游失败 | `release` 后 `reserved` 归零 |
| 流中断 | `settle` 部分用量，`estimated=true` |
| 结算时余额已不足 | 允许为负，下次预扣失败 |
| Redis 重启（未持久化） | `reserved` 丢失 → 启动时按 `quota_reservation` 表重建 |
