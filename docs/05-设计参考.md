# 设计参考与差异

> 本项目在架构设计上参考了若干开源项目的思路，**未复制任何代码**。
> 记录于此便于理解设计来源与取舍。

---

## 参考项目

| 项目 | 技术栈 | 定位 | 许可证 |
|---|---|---|---|
| [cc-router](https://github.com/finch-xu/cc-router) | Rust + Tauri + React | 本地桌面聚合网关，虚拟模型与订阅调度 | MIT |
| [new-api](https://github.com/QuantumNous/new-api) | Go + Gin + React | 自托管 AI 网关，四协议互转、渠道路由、配额计费 | AGPL-3.0 |
| [sub2api](https://github.com/Wei-Shaw/sub2api) | Go + Gin + Vue | 订阅额度分发，多账号池、粘性会话、并发控制 | LGPL-3.0 |
| [fizz-gateway-node](https://github.com/fizzgate/fizz-gateway-node) | Java + Spring Boot | 企业级 API 聚合网关，插件化、限流熔断 | AGPL-3.0 |

## 借鉴了什么

### 来自 cc-router

- **虚拟模型抽象**：把 `opus/sonnet/haiku` 抽象成槽位，同一虚拟模型绑多个真实模型
- **会话标识提取顺序**：`x-claude-code-session-id` → `metadata.user_id`，
  Codex 用 `prompt_cache_key` → `session_id`
- **调度三模式的取舍论证**：顺序（榨干小额套餐且缓存好）/ 轮询（均衡）/ 亲和（均衡且不丢缓存）
- **"有原生端点就优先走原生"** 的主张 → 本项目的双车道设计

### 来自 new-api

- **分层结构**：`router / middleware / controller / relay / service / model`
- **协议转换独立成模块**（RelayKit）：本项目对应 `protocol/` 包，零 Spring 依赖
- **诚实地列出不支持项**：README 明确声明"协议特定工具与字段可能无法精确映射"
- **渠道亲和**：在优先级+权重之外提供渠道粘性

### 来自 sub2api

- **分层限流**：用户级 + 账号级并发、请求速率、token 速率
- **账号状态机**：`401 → 临时摘除`、`403 → 权限失败不重试`、`429 → 按 Retry-After 冷却`
- **配置安全**：`url_allowlist`（防 SSRF）、`trusted_proxies`（防伪造 XFF）

### 来自 fizz-gateway-node

- **无状态节点 + 配置自动同步**：本项目对应"配置快照 + AtomicReference 热替换"
- **插件链式拦截**：本项目把鉴权、限流、配额设计成可串联的 WebFilter
- **多级限流**：服务级 / 接口级 / APP_ID 级 / IP 级

## 本项目的差异

| 能力 | 说明 |
|---|---|
| **双车道转发** | 同协议零拷贝透传，跨协议才走 IR；按渠道可开关。多数项目以翻译为主 |
| **两阶段配额 + 幂等 reservation** | 预扣/结算/释放三态 + 补偿与对账闭环 |
| **自动降权（区别于熔断）** | 健康度驱动权重缩放，保留探测流量；与熔断的开关语义分离 |
| **多模态计价** | 图片按张、音频按秒，与 token 计价叠加，含倍率与折扣 |
| **路由决策可回放** | 每条请求记录候选、过滤原因、选中、重试 |
| **协议一致性夹具测试** | 真实录制的 SSE 样本驱动，覆盖三协议编解码 |
| **可验证的性能口径** | 明确区分"网关附加延迟"与"端到端 TTFT"，压测方法可复现 |
