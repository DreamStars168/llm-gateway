# 01 总体架构设计

> 项目代号：`llm-gateway`（简历名：LLM 多模型接入网关与对话平台）
> 技术基线：Java 17 / Spring Boot 3.3 / WebFlux / Reactor Netty / Redis 7 / MySQL 8 / RabbitMQ 3.13 / Vue 3 + TS
> 目标：单机 1000 并发 SSE 长连接下，网关自身附加延迟 P99 < 10ms，配额扣减零超卖。

---

## 1. 设计目标与非目标

### 1.1 目标

| 编号 | 目标 | 可验证口径 |
|---|---|---|
| G1 | 一个入口接入多家上游 | 同一套 API Key 可调用 OpenAI / Anthropic / Gemini 及任意兼容端点 |
| G2 | 四种主流协议互通 | 入口 × 出口 = 4×4 组合中，文本/工具/图片三条链路可用（见 02 文档矩阵） |
| G3 | 流式零阻塞 | SSE 首字节透传，不在网关聚合完整响应 |
| G4 | 路由可控可观测 | 优先级 + 权重 + 会话亲和 + 熔断 + 故障转移，每次决策可回放 |
| G5 | 计费不超卖 | 并发 1000 次扣减，余额 100 时恰好成功 100 次 |
| G6 | 低附加延迟 | 网关附加延迟 P99 < 10ms（不含上游耗时） |
| G7 | 配置热生效 | 渠道/价格/路由变更 10s 内全节点生效，无需重启 |
| G8 | 对话平台 | 多模型并排对比、参数实时调节、Prompt 版本归档 |

### 1.2 非目标（第一期明确不做）

- 不做模型训练/推理，只做接入与调度。
- 不自建支付渠道（预留充值回调接口，不对接具体支付 SDK）。
- 不做多租户计费发票、不做代理商分润体系。
- 不做 Prompt 内容审核（仅预留审核 Filter 扩展点）。
- 不做 Responses WebSocket 入口（第二期，见 07 路线图）。

### 2.1 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| 接入层 `auth/` | API Key 校验、租户解析、限流、TraceId 注入、请求体大小限制 | 禁止查库、禁止反序列化 messages |
| 协议适配层 `protocol/` | 入口报文 → 规范请求（IR）；IR → 出口报文；SSE 编解码 | 禁止做路由决策 |
| 路由层 `routing/` | 模型解析、候选集过滤、亲和、权重、熔断、并发闸门 | 禁止发 HTTP |
| 转发层 `relay/` | 建连、发送、流式回写、重试边界、用量采集 | 禁止写 MySQL |
| 结算旁路 `usage/` | 预扣/结算、异步落库、聚合、对账 | 禁止进入请求关键路径（除预扣 Lua） |
| 控制面 `admin/` | 渠道/模型/价格/Key/日志/看板 CRUD | 禁止在数据面被同步调用 |

### 2.2 关键决策（ADR 摘要）

| # | 决策 | 备选方案 | 选择理由 |
|---|---|---|---|
| D1 | 自研转发管线，HTTP 层用 `RouterFunction` + `WebFilter` | Spring Cloud Gateway | SCG 改 body 必须全量反序列化，SSE 长连接下 `ModifyResponseBody` 会破坏流式；自研可做到字节级透传，附加延迟可控 |
| D2 | 双车道：原生透传优先，必要时翻译 | 全部走 IR 统一翻译 | 全量翻译会丢 `cache_control`、`thinking`、`anthropic-beta` 等原厂特性，且 CPU 开销大；cc-router 实践也证明"有原生端点就走原生" |
| D3 | 数据面不碰 MySQL，热数据走 Caffeine + Redis | 每请求查库 | 单机 1000 并发下 DB 连接池与 RT 不可控；配置由控制面推送快照 |
| D4 | 配额两阶段：预扣 + 结算 | 响应后一次性扣 | 流式场景用量在结束时才可知，一次性扣会在并发下透支 |
| D5 | 用量异步落库（RabbitMQ） | 同步写库 | 写库抖动会直接抬高 P99；异步 + 本地 outbox 兜底保证不丢 |
| D6 | 熔断按「渠道 × 模型」维度 | 按渠道全局 | 同一渠道不同模型可用性差异大（如某模型 429 而其他正常） |
| D7 | 会话亲和用 Redis 存映射 | 一致性哈希 | 节点扩缩容时一致性哈希会大面积失效；Redis 映射可显式 TTL 与失效 |
| D8 | 控制面用 MyBatis-Plus 阻塞式，独立线程池 | 全栈 R2DBC | 管理端 QPS 极低，R2DBC 生态与调试成本高；只要不落在 event loop 上即可 |

## 3. 请求全链路时序

### 3.1 流式请求（快车道，同协议透传）

```
Client          Gateway                                              Upstream
  │  POST /v1/messages (stream=true)                                  │
  ├───────────────▶│                                                  │
  │                │ 1. AuthFilter: key 前缀 → Caffeine 命中(0.2ms)     │
  │                │ 2. BodyBuffer: 读取并缓存(上限 32MB)，JsonPeek 取 model
  │                │ 3. RouteResolver: 别名→虚拟模型→候选渠道(0.3ms)     │
  │                │ 4. QuotaService.reserve(): Lua 原子预扣(0.8ms)      │
  │                │ 5. 选渠道: 优先级→权重→亲和→熔断状态                │
  │                │ 6. 改写 model 字段，其余字节原样                     │
  │                ├─────────────────────────────────────────────────▶│
  │                │            200 + text/event-stream               │
  │                │◀─────────────────────────────────────────────────┤
  │   SSE 帧       │ 7. 逐帧转发（不解析、不聚合），顺带统计字节数         │
  │◀───────────────┤                                                  │
  │                │ 8. 流结束：解析 usage 帧 → settle → MQ 异步落库      │
  │                │ 9. 记录 TTFT / 总耗时 / 渠道 / 重试次数              │
```

### 3.2 跨协议请求（慢车道，翻译）

```
Client(OpenAI Chat) → Ingress: OpenAiChatIngress.parse → CanonicalRequest
                    → RouteResolver（同 3.1）
                    → Egress: AnthropicEgress.build → 上游 /v1/messages
                    → 上游 SSE(Anthropic 事件) → AnthropicSseDecoder
                    → CanonicalChunk 流 → OpenAiChatSseEncoder → 客户端
```

### 3.3 失败与重试边界

```
                ┌── 连接失败 / 5xx / 429 ──▶ 未向客户端写出任何字节 ──▶ 可换渠道重试(≤N)
请求 ──▶ 发送 ──┤
                └── 已写出首字节 ──▶ 不可重试 ──▶ 发 error 事件并关闭，记录部分用量
```

> 幂等边界：**首个响应字节写出的瞬间**。此前失败可重试；此后任何失败只能终止并如实计费（已产生的上游 token 由上游计费，网关按已知增量估算）。

## 5. 线程与背压模型

| 资源 | 配置 | 说明 |
|---|---|---|
| Netty event loop | `ReactorNetty` 默认 = CPU 核数（≥4） | 全部 IO 在此，**禁止阻塞** |
| 上游连接池 | 每渠道 `maxConnections=500`，`pendingAcquireTimeout=5s`，`maxIdleTime=30s`，`leasingStrategy=lifo` | 1000 并发 SSE 需要 ≥1000 条上游连接，按渠道分摊 |
| 客户端并发闸门 | 单实例 `maxConcurrentStreams=8000`，信号量不足返回 429 | 防止 OOM，先保护自己 |
| 渠道并发闸门 | 每渠道 `maxInflight`（默认 200），超出换下一候选 | 保护上游配额 |
| 控制面线程池 | `admin-io` 固定 16 线程（JDBC） | 与 event loop 隔离 |
| 消费者线程池 | `usage-consumer` 8 线程，prefetch=32 | RabbitMQ 手动 ack |
| 直接内存 | `-XX:MaxDirectMemorySize=1g`，池化 `PooledByteBufAllocator` | SSE 转发不复制 body |

**零拷贝要点**：上游 `HttpClientResponse` 的 `ByteBufFlux` 统一用 `NettyDataBufferFactory.wrap(byteBuf)` 包装后写出，避免 `DataBufferUtils.join`；只在需要改写时（如注入 usage 帧）才复制单帧。

## 6. 部署拓扑

### 6.1 开发/演示（docker-compose）

```
nginx:8080 ──▶ gateway-1:8081 ─┐
              gateway-2:8082 ─┼─▶ mysql:3306 / redis:6379 / rabbitmq:5672
              console:5173(dev)┘
              mock-upstream:9000（压测时启用）
```

### 6.2 生产（最小高可用）

- gateway 无状态，≥2 副本，前置 Nginx/SLB（关闭 `proxy_buffering`，`proxy_read_timeout 600s`）。
- Redis 主从 + Sentinel；配额 Lua 走主节点（写）。
- MySQL 主从，读走从库（日志查询）。
- RabbitMQ 3 节点仲裁队列（或单节点 + 镜像队列，按规模取舍）。
- 配置版本号存 Redis，节点订阅 `cfg:invalidate` 频道。

### 6.3 Nginx 关键片段

```nginx
location /v1/ {
    proxy_pass http://gateway_pool;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;          # SSE 必须关闭
    proxy_cache off;
    proxy_read_timeout 600s;
    chunked_transfer_encoding on;
}
```

## 7. 容量与延迟预算

### 7.1 单机 1000 并发 SSE 的资源估算

| 项 | 估算 |
|---|---|
| 连接内存 | 每连接 ~12KB（读缓冲 8KB + 写缓冲 4KB）→ 1000 连接 ≈ 12MB |
| 上游连接 | 1000 条，HTTP/1.1 或 HTTP/2 多路复用（Gemini/OpenAI 支持 h2 时可降到 ~100 条） |
| 出向带宽 | 每流 20~200 token/s ≈ 1~8KB/s → 1000 流 ≈ 8MB/s |
| CPU | 透传模式几乎只做字节搬运，1 核可支撑 ~1500 并发空闲流 |

### 7.2 附加延迟预算（目标 P99 < 10ms）

| 阶段 | P50 | P99 | 优化手段 |
|---|---|---|---|
| Key 校验 | 0.1ms | 0.3ms | Caffeine 本地缓存，30s TTL |
| 请求体读取 + model 提取 | 0.2ms | 0.6ms | 已缓冲则仅 Jackson 流式扫一个字段 |
| 路由决策 | 0.1ms | 0.3ms | 预编译不可变路由表，`AtomicReference` 整体替换 |
| 配额预扣（Redis Lua） | 0.4ms | 1.2ms | 单次 RTT、单脚本多 key、同机房部署 |
| 渠道选择 + 熔断判断 | 0.05ms | 0.2ms | 本地滑动窗口 |
| 连接获取 | 0.2ms | 3ms | 连接池预热，`lifo` 复用 |
| 请求构造与写出 | 0.2ms | 0.8ms | 透传模式零拷贝 |
| **合计** | **~1.3ms** | **~6.4ms** | 留 3.6ms 余量 |

> 度量口径：`gateway_added_latency = t_upstream_request_sent - t_request_received`（透传模式），以及 `ttft_client = 首帧写出时间 - 请求到达时间`（含上游 TTFT）。压测报告必须同时给出两者，避免把上游耗时算到网关头上。

## 8. 安全设计

| 面 | 措施 |
|---|---|
| API Key | 仅存 `SHA-256(secret)`；明文只在创建时返回一次；前缀 `sk-lg-{keyId}-` 用于索引 |
| 上游凭证 | AES-256-GCM 加密存库，KEK 来自环境变量/KMS，密文带 `keyVersion` 支持轮换 |
| 管理端 | Spring Security + JWT（短期 access + refresh），RBAC：`SUPER_ADMIN / ADMIN / OPERATOR / VIEWER` |
| 越权 | API Key 绑定 `group`，只能访问该 group 下的渠道与模型；模型白名单二次校验 |
| SSRF | 渠道 `baseUrl` 白名单 + 禁止私网/回环（可由管理员显式放行内网，用于自建 vLLM） |
| 日志脱敏 | 默认不落请求体；开启后对 `authorization`、`x-api-key`、图片 base64 做掩码；可选 PII 正则 |
| 重放 | 管理端写操作要求 `Idempotency-Key`；审计日志记录操作者/IP/UA |
| 限流 | 三层：IP（边缘）/ Key（分钟级）/ 租户（日额度） |

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 各厂商 SSE 方言差异（心跳、`[DONE]`、空行、CRLF） | 客户端解析失败 | 统一 `SseLineParser` + 协议夹具回归测试（录制的真实响应） |
| 上游 usage 缺失或不准 | 计费偏差 | 优先用上游 usage；缺失时用 jtokkit 估算并标记 `estimated=true`；对账任务修正 |
| Redis 故障 | 配额不可用 | 降级策略：`fail-closed`（拒绝）或 `fail-open`（放行+记账后补），按租户配置 |
| 长连接导致发布时连接被切 | 用户体验 | 优雅下线：先从 LB 摘除，等待 `maxDrainTime=120s` |
| 协议翻译丢字段 | 功能缺失 | 翻译路径只对"必要字段"负责，文档明示不支持项；优先引导用户走原生端点 |
| 许可污染 | 法务风险 | 只借鉴设计，不复制 AGPL/LGPL 代码（见 08 文档） |
