# 路由、调度与计费

---

## 一、路由

### 1.1 领域模型

```
Tenant 1 ── n ApiKey
Tenant 1 ── n Group ── n Channel      （Group 是权限与计费边界）
VirtualModel 1 ── n ModelRoute ── 1 Channel
```

路由挂在 `model_route` 而不是 `channel`：同一渠道可给不同虚拟模型映射不同上游模型与倍率；
同一虚拟模型可挂多个渠道形成候选集。

### 1.2 四级流水线

```
请求(virtualModel, groupId, sessionKey)
   │
   ├─① 候选集：group 内 + route 启用 + 渠道启用 + 协议兼容
   │
   ├─② 会话亲和：sessionKey → sticky 映射；命中且健康则直接复用
   │
   ├─③ 健康过滤：熔断 / 并发闸门 / 降权
   │
   ├─④ 优先级分层：只在最高优先级层内做加权（硬分层）
   │
   └─▶ 平滑加权轮询（SWRR）
```

### 1.3 平滑加权轮询

经典算法，避免"权重 5:1 时前 5 个请求全打 A"的突发：

```java
// 每次选择：current += weight; 选 current 最大者; 选中者 current -= totalWeight
record Node(int weight, AtomicInteger current) {}
```

状态存本地（每实例独立），无需 Redis，多实例天然分摊。
缺点是小流量下有偏斜，大流量下趋近均衡。

### 1.4 会话亲和（Sticky）

**为什么需要**：多账号时若同一会话被轮询到不同上游，各家 prompt cache **按账号隔离**，
切换即失效。一次 10K 输入的请求，缓存命中时输入价按 `cacheRead`（约 1/10）计，
乱切会让成本**翻 5~10 倍**，TTFT 也显著变长。

**会话标识提取（按优先级）**：

| 优先级 | 来源 | 客户端 |
|---|---|---|
| 1 | `x-claude-code-session-id` | Claude Code |
| 2 | `session_id` | Codex CLI |
| 3 | `x-session-id` | 通用 |
| 4 | body `prompt_cache_key` | Codex 部分版本 |
| 5 | body `user` | OpenAI 兼容 |
| 6 | body `metadata.user_id` | Anthropic SDK |
| 7 | 首条消息内容 hash | 兜底 |

**两级存储**：

```
请求 → 本地 Caffeine（零网络往返，命中率 >95%）
         │ miss
         ▼
       Redis（跨实例共享，TTL 30min 滑动）
```

写路径：请求**成功后**才绑定（失败/熔断的渠道不应被钉住）。
关键路径用 `peekLocal()` 同步读 Caffeine，未命中直接退化轮询，由请求结束补写。

**亲和为何能压过优先级**：假设会话已绑定备渠道，严格按优先级会切回主渠道，缓存全失效。
缓存收益（成本降 5~10 倍）远大于"用上更便宜渠道"，所以亲和排在优先级之前。
**前提**：该渠道必须健康（未熔断、未打满）。

### 1.5 熔断

粒度：**渠道 × 上游模型**。某渠道的 `gpt-4o` 限流不代表 `gpt-4o-mini` 不可用。

```
                失败率≥50% 且 窗口内≥20 次
   CLOSED ────────────────────────────────▶ OPEN
     ▲                                        │
     │  连续 3 次探测成功                       │ 冷却 30s
     └────────────────────────────────── HALF_OPEN
                            （放行 3 个探测请求）
```

- 滑动窗口：本地 RingBuffer，10s 窗口
- 失败判定：连接失败、5xx、429、首字节超时；**4xx（400/401/403）不算渠道失败**
- 冷却：429 按 `Retry-After`，5xx 15s，连接失败 10s，401/403 标记 Key 失效

### 1.6 自动降权

**与熔断的区别**：

| | 熔断 | 自动降权 |
|---|---|---|
| 行为 | 开关（摘除 / 半开） | 节流（权重按健康度缩放） |
| 目的 | 快速止损 | 让"半死不活"的渠道少接流量但保留探测 |

算法（指数滑动健康分 `health ∈ [0,1]`）：

```
成功:   health += (1 - health) × 0.1
严重失败: health -= health × 0.5     （5xx / 连接失败）
轻度失败: health -= health × 0.15    （429 限流）
权重 = baseWeight × max(0.05, health)
```

指数滑动的好处：连续失败快速降到底（幂等收敛），偶发失败只轻微影响。
`minRatio=0.05` 保证再差也保留 5% 流量用于探测自愈。
空闲 5 分钟后缓慢回归 1.0，避免历史故障永久压低权重。

### 1.7 重试与故障转移

**硬约束：只在「尚未向客户端写出任何字节」时重试**，否则会拼接出脏流。

| 阶段 | 错误 | 是否换渠道 |
|---|---|---|
| 建连 | ConnectException / DNS | 是 |
| 发送后未响应 | 首字节超时（默认 60s） | 是 |
| 响应 429 | RateLimit | 是（优先换 Key） |
| 响应 5xx / 529 | ServerError | 是 |
| 响应 400 / 422 | 请求非法 | 否（换渠道也一样错） |
| 响应 401 / 403 | 凭证问题 | 是（换 Key）+ 标记失效 |
| **已写出首字节** | 任何错误 | **否** |

实现：`AtomicBoolean firstByteWritten` 在首帧写出时置位，之后任何失败只记录不重试。

### 1.8 四层限流

| 层 | Key | 算法 | 目的 |
|---|---|---|---|
| 全局入站 | 实例 | 信号量 | OOM 前自我保护 |
| 租户 RPM/TPM | `tenant:{id}:{minute}` | Redis 固定窗口 | 商业套餐限速 |
| API Key | `key:{id}:{minute}` | Redis 滑动窗口 | 精细限速 |
| 渠道并发 | 本地 Semaphore | 直接计数 | 保护上游 |

渠道闸门必须**非阻塞获取**（`tryAcquire`），失败即换候选，绝不排队——排队会放大尾延迟。

## 二、计费

### 2.1 两阶段配额

流式请求的最终 token 数在响应结束时才知道：
- 只在结束时扣 → 并发下必然超卖
- 只按预估扣且不修正 → 预估偏差导致浪费或超卖

```
   ┌──────────┐   reserve(est)    ┌───────────┐   settle(actual)   ┌───────────┐
   │  IDLE    │──────────────────▶│ RESERVED  │───────────────────▶│ SETTLED   │
   └──────────┘                   └───────────┘                    └───────────┘
                                        │
                                        │ release（上游失败/取消）
                                        ▼
                                  ┌───────────┐
                                  │ RELEASED  │
                                  └───────────┘
```

- `reservationId = requestId`（幂等键）
- 预扣额 = `max_tokens` 上限估算 × 1.2 安全系数
- 结算 = `actual - est` 的差额修正；允许余额为负（欠款），下次预扣自然失败

### 2.2 Redis 数据结构

```
quota:{tenantId}:balance       STRING  (micro-USD，可为负)
quota:{tenantId}:reserved      STRING  (在途预扣总额)
reservation:{requestId}        HASH    {tenant, key, amount, status, ts}
```

**关键**：余额校验必须用 `balance - reserved >= amount`。
只校验 `balance` 会在并发下超卖——`reserved` 的存在保证不会"看到同一个余额都放行"。

### 2.3 原子预扣（Lua）

```lua
if redis.call('EXISTS', KEYS[3]) == 1 then return 2 end   -- 幂等
local bal = tonumber(redis.call('GET', KEYS[1]) or '0')
local res = tonumber(redis.call('GET', KEYS[2]) or '0')
if bal - res < tonumber(ARGV[1]) then return 0 end        -- 余额不足
redis.call('INCRBY', KEYS[2], ARGV[1])
redis.call('HSET', KEYS[3], 'amount', ARGV[1], 'status', 'RESERVED')
redis.call('EXPIRE', KEYS[3], ARGV[2])
return 1
```

单次 RTT，脚本内无网络调用，Redis 单线程保证原子性。`EXISTS` 幂等使重试安全。

### 2.4 降级策略

预扣是请求关键路径上唯一的同步 Redis 调用，超时（默认 800ms）后：

| 模式 | 行为 | 适用 |
|---|---|---|
| `FAIL_OPEN` | 放行请求，请求结束照常结算 | 可用性优先 |
| `FAIL_CLOSED` | 返回 503 | 资金安全优先 |

`FAIL_OPEN` 不等于"白送"：`UsageEvent` 带 `degraded=true`，
消费者发现 Redis 无预扣记录时走"直接扣减"分支，保证账最终能对上。

### 2.5 分级定价

```json
{
  "claude-sonnet-4": {
    "tiers": [
      { "inputTokensLte": 200000, "input": "3.0", "output": "15.0",
        "cacheWrite": "3.75", "cacheRead": "0.30" },
      { "inputTokensLte": null,   "input": "6.0", "output": "22.5",
        "cacheWrite": "7.50", "cacheRead": "0.60" }
    ],
    "channelMultiplier": "1.0",
    "groupDiscount": "1.0",
    "multimodal": { "imagePerUnit": "0.04", "audioPerSecond": "0.0001" }
  }
}
```

- **单位**：USD / 1M tokens
- **档位**：按顺序匹配，命中第一个满足条件的；`null` 表示兜底档
- **长上下文溢价**：输入 > 200K 时单价翻倍（Anthropic 真实规则）
- **缓存独立计价**：`cacheRead` 通常是 `input` 的 1/10

### 2.6 计算精度

```java
// 全部 BigDecimal，禁止 double
BigDecimal sum = input.mul(inputRate)
    .add(output.mul(outputRate))
    .add(cacheRead.mul(cacheReadRate));
BigDecimal usd = sum.divide(ONE_MILLION, 12, HALF_UP);
BigDecimal finalUsd = usd.multiply(multiplier).multiply(discount);
long micro = finalUsd.multiply(MICRO).setScale(0, HALF_UP).longValue();
```

中间保留 12 位小数，最终转 micro-USD（long）。负数保护 `Math.max(0L, micro)`。

### 2.7 多模态计价

图片/音频成本与 token 无线性关系（如 GPT-4o 生成一张 1024×1024 图是固定 $0.04）。
混进 token 单价会算错，因此独立一套：

```java
record MultimodalUsage(int images, double audioSeconds, double videoSeconds)

// 多模态部分是绝对值 USD，不再除以 1M
usd = usd.add(imagePerUnit × images)
         .add(audioPerSecond × audioSeconds);
```

**用量从哪来**：上游只返回 token 用量，不告诉你有几张图。
`MultimodalUsageExtractor` 从请求体递归统计（兼容三种协议结构），
音频优先读 `duration_seconds`，缺失时按 base64 长度估算。

## 三、数据模型

核心表：

| 表 | 用途 |
|---|---|
| `channel` | 上游渠道（协议、baseUrl、优先级、权重、并发上限） |
| `model_route` | 虚拟模型 → 真实模型 + 渠道的映射 |
| `api_key` | 客户端 Key（只存 SHA-256 哈希） |
| `price_rule` | 定价规则（JSON 档位） |
| `quota_reservation` | 预扣流水（7 天） |
| `relay_log` | 请求明细（按月分区） |
| `usage_daily` | 日聚合 |
| `prompt_version` | Playground Prompt 归档 |

完整 DDL 见 [`db/schema.sql`](../db/schema.sql)。

**索引原则**：

- 列表查询必须带时间范围（否则分区裁剪失败）
- `relay_log` 只存元数据，不存请求/响应体
- 大字段用 JSON，不建索引

## 四、实测验证

### 4.1 零超卖

```
初始余额 100.00 USD，单次预扣 1.00 USD，并发 1000
→ 成功 100 次，余额不足 900 次，重复 0 次
→ balance 与 reserved 均精确，无泄漏
```

### 4.2 幂等闭环

```
预扣 2.0 → 重复预扣(返回2) → 结算 1.5 → 重复结算(返回2) → 释放(返回2)
→ 最终 balance = 8.5 USD，reserved = 0
```

### 4.3 会话亲和

```
会话 sess-AAA 连发 6 次：
  第 1 次 stickyHit=false（未绑定）
  第 2~6 次 stickyHit=true，全部命中 anthropic-main

10 个不同会话（同优先级 100:100 权重）：精确 5:5 分散
```

### 4.4 计费精度

| 模型 | Token | 理论成本 | 实测 |
|---|---|---|---|
| claude-sonnet-4 | 23 / 9 | 23×3 + 9×15 = 204 | **204** ✅ |
| gpt-4o-mini | 31 / 12 | 31×0.15 + 12×0.6 = 11.65 | **12** ✅ |
| gemini-2.5-pro | 27 / 10 | 27×1.25 + 10×10 = 133.75 | **134** ✅ |
| claude-sonnet-4 + 1图 | 23 / 9 | 204 + 40000 = 40204 | **40204** ✅ |

### 4.5 自动降权

```
连续 10 次严重失败 → health < 0.1，权重降至 minRatio，但不为 0
恢复 20 次成功 → health > 0.8
200 次选路中，降权渠道被选中 < 80 次（原本应约 100 次）
```
