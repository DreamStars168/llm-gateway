# 架构设计

> 技术栈：Java 17 / Spring Boot 3.3 / WebFlux / Reactor Netty / Redis 7 / MySQL 8 / RabbitMQ 3.13 / Vue 3 + TS

## 2. 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| 接入层 `auth/` | API Key 校验、租户解析、限流、TraceId | 禁止查库、禁止反序列化 messages |
| 协议层 `protocol/` | 入口报文 → IR；IR → 出口报文；SSE 编解码 | 禁止做路由决策 |
| 路由层 `routing/` | 候选过滤、亲和、权重、熔断、降权、闸门 | 禁止发 HTTP |
| 转发层 `relay/` | 建连、发送、流式回写、用量采集 | 禁止写 MySQL |
| 结算旁路 `usage/` | 预扣/结算、异步落库、聚合 | 禁止进入请求关键路径 |
| 控制面 `admin/` | 渠道/模型/价格/日志 CRUD | 禁止被数据面同步调用 |

## 3. 关键技术决策

### D1 · 不用 Spring Cloud Gateway

**问题**：SCG 的 `ModifyResponseBody` 必须全量反序列化响应体，在 SSE 长连接场景下会破坏流式并显著抬高延迟。

**选择**：基于 `RouterFunction` + `WebFilter` 自研转发管线，实现字节级透传。

**代价**：需要自己处理连接池、重试、错误映射。收益是附加延迟可控（实测 P99 5.1ms）。

### D2 · 双车道转发

| 场景 | 路径 | 开销 |
|---|---|---|
| 入口协议 == 出口协议 | 只改 `model` 字段，字节级转发 | 零解析、零拷贝 |
| 入口 ≠ 出口 | Ingress 解析 → IR → Egress 构造 | 一次序列化 + 一次反序列化 |

大多数网关选择"全部翻译"，代价是每个请求都要过一遍 JSON。这里把透传做成默认路径。

### D3 · 数据面不碰 MySQL

热数据（API Key、路由表、价格表）走 Caffeine 本地缓存，配置变更加版本号广播失效。
单机 200 并发下，DB 连接池与 RT 不可控，不能放在请求路径上。

### D4 · 配额两阶段提交

流式请求的最终 token 数在响应结束时才知道：
- 只按预估扣 → 并发下透支
- 只在结束时扣 → 超卖

因此必须 `reserve → settle / release`。详见 [路由与计费](03-路由与计费.md)。

### D5 · 用量异步落库

写库抖动会直接抬高 P99。通过 RabbitMQ 承接，配合幂等消费 + 本地缓冲兜底。
**用量统计失败绝不能影响用户的对话请求**。

### D6 · 熔断按「渠道 × 模型」

同一渠道不同模型可用性差异大（某模型 429 而其他正常）。整渠道熔断会造成误伤。

### D7 · 会话亲和用 Redis + 本地两级

一致性哈希在节点扩缩容时会大面积失效；Redis 映射可显式 TTL 与主动失效。
本地 Caffeine 做一级缓存，命中时零网络往返。

### D8 · 控制面阻塞式，数据面响应式

管理端 QPS 极低，用 JDBC + 独立线程池（`admin-io`）即可；
数据面全链路 WebFlux，**禁止任何阻塞调用**。

## 4. 请求全链路时序（流式透传）

```
Client          Gateway                                              Upstream
  │  POST /v1/messages (stream=true)                                  │
  ├───────────────▶│                                                  │
  │                │ 1. AuthFilter: key → Caffeine 命中(0.2ms)         │
  │                │ 2. BodyBuffer: 读取并缓存，提取 model 字段         │
  │                │ 3. RouteResolver: 候选 → 亲和 → 权重(0.3ms)        │
  │                │ 4. QuotaService.reserve(): Lua 原子预扣(0.8ms)     │
  │                │ 5. 改写 model 字段，其余字节原样                    │
  │                ├─────────────────────────────────────────────────▶│
  │                │            200 + text/event-stream               │
  │                │◀─────────────────────────────────────────────────┤
  │   SSE 帧       │ 6. 逐帧转发（不解析、不聚合），统计字节数           │
  │◀───────────────┤                                                  │
  │                │ 7. 流结束：提取 usage → settle → 异步落库          │
  │                │ 8. 记录 TTFT / 总耗时 / 渠道 / 重试次数            │
```

## 5. 延迟预算

| 阶段 | P50 | P99 | 优化手段 |
|---|---|---|---|
| Key 校验 | 0.1ms | 0.3ms | Caffeine 本地缓存 |
| 请求体读取 + model 提取 | 0.2ms | 0.6ms | 已缓冲则仅扫一个字段 |
| 路由决策 | 0.1ms | 0.3ms | 预编译不可变路由表 |
| 配额预扣（Redis Lua） | 0.4ms | 1.2ms | 单次 RTT、同机房 |
| 渠道选择 + 熔断判断 | 0.05ms | 0.2ms | 本地滑动窗口 |
| 连接获取 | 0.2ms | 3ms | 连接池预热 |
| 请求构造与写出 | 0.2ms | 0.8ms | 透传模式零拷贝 |
| **合计** | **~1.3ms** | **~6.4ms** | 实测 P99 5.1ms |

> 度量口径：`附加延迟 = t_upstream_sent - t_request_received`。
> 不含上游耗时，避免把上游慢算到网关头上。

## 6. 线程与背压

| 资源 | 配置 | 说明 |
|---|---|---|
| Netty event loop | 默认 = CPU 核数 | 全部 IO 在此，**禁止阻塞** |
| 上游连接池 | `maxConnections=2000`，`lifo` 复用 | 长连接场景需足够连接数 |
| 客户端并发闸门 | 单实例上限，信号量不足返回 429 | 防 OOM |
| 渠道并发闸门 | 每渠道 `maxInflight`，超出换候选 | 保护上游 |
| 控制面线程池 | `admin-io` 固定 16 线程 | 与 event loop 隔离 |
| 消费者线程池 | `usage-consumer`，prefetch=32 | 手动 ack |

**零拷贝要点**：上游 `ByteBufFlux` 直接用 `NettyDataBufferFactory.wrap()` 包装后写出，
避免 `DataBufferUtils.join`；只在需要改写时才复制单帧。

## 7. 包结构

```
gateway-server/src/main/java/com/zhouyu/gateway/
├── auth/              # API Key 鉴权（Caffeine 缓存）
├── billing/           # 定价规则与成本计算
├── common/            # 错误码、异常
├── config/            # 配置加载、安全
├── domain/            # 领域模型（Channel/ModelRoute/Protocol）
├── observability/     # Micrometer 指标
├── playground/        # Prompt 版本归档
├── protocol/          # 协议适配
│   ├── canonical/     # IR 规范模型
│   ├── anthropic/     # Messages 解析/编码
│   ├── openai/        # Chat Completions
│   ├── gemini/        # generateContent
│   └── sse/           # SSE 帧解析与桥接
├── quota/             # 两阶段配额
```

**设计约束**：`protocol/` 包零依赖 Spring，可独立单测与复用。

## 8. 部署拓扑

### 单机（开发 / 演示）

```
docker compose up -d --build
  ├── gateway      :18081
  ├── mysql        :13306
  ├── redis        :6379
  ├── rabbitmq     :5672 / 15672
  └── mock-*       :9000 / 9001
```

### 生产（最小高可用）

- gateway 无状态，≥2 副本，前置 Nginx/SLB
- **Nginx 必须关闭 `proxy_buffering`**，否则 SSE 会被缓冲
- Redis 主从 + Sentinel；配额 Lua 走主节点
- MySQL 主从，读走从库
- 配置版本号存 Redis，节点订阅 `cfg:invalidate`

```nginx
location /v1/ {
    proxy_pass http://gateway_pool;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;          # SSE 必须
    proxy_read_timeout 600s;
    chunked_transfer_encoding on;
}
```

## 9. 容量估算

| 项 | 估算（单实例 4C8G） |
|---|---|
| 连接内存 | 每连接 ~12KB（读 8KB + 写 4KB） |
| 上游连接 | 1000 并发 → 1000 条（HTTP/2 多路复用可降至 ~100） |
| 出向带宽 | 每流 20~200 token/s ≈ 1~8KB/s |
| CPU | 透传模式 1 核可支撑 ~1500 并发空闲流 |
| **实测上限** | **200 并发零错误**（受 Redis 单连接限制，见压测报告） |
