# 07 可观测性、运维与容量规划

> 目标：出问题 1 分钟内定位到"哪个渠道、哪个模型、哪个租户、哪一步慢"。

---

## 1. 指标体系

### 1.1 四大黄金信号

| 信号 | 指标 | 告警阈值 |
|---|---|---|
| 流量 | `gateway_requests_total{protocol_in,model,channel}` | 突降 50% / 突增 300% |
| 错误 | `gateway_errors_total{code,channel}`、`gateway_error_rate` | > 5% 持续 3min |
| 延迟 | `gateway_added_latency`、`gateway_ttft_seconds`、`gateway_total_seconds` | 附加延迟 P99 > 10ms |
| 饱和度 | `gateway_inflight`、`channel_inflight{channel}`、`executor_queue{pool}` | 闸门 > 80% 持续 5min |

### 1.2 业务指标

| 指标 | 说明 |
|---|---|
| `gateway_tokens_total{type=input\|output\|cached\|reasoning}` | 按模型/渠道/租户 |
| `gateway_cost_micro_total{model,channel,tenant}` | 成本（micro-USD） |
| `gateway_route_failover_total{from,to,reason}` | 故障转移次数 |
| `gateway_breaker_state{channel,model}` | 0=CLOSED 1=HALF_OPEN 2=OPEN |
| `gateway_sticky_hit_ratio` | 亲和命中率 |
| `gateway_sticky_rebind_total` | 亲和被覆盖次数（抖动指标） |
| `gateway_quota_reserve_seconds` | 预扣耗时 |
| `gateway_usage_publish_fail_total` | MQ 发布失败 |
| `gateway_usage_dlq_size` | 死信堆积 |

### 1.3 指标埋点位置

```java
// relay/RelayPipeline.java
Timer.Sample sample = Timer.start(meterRegistry);
Counter.builder("gateway.requests")
       .tag("protocol_in", ctx.protocol().name())
       .tag("model", req.virtualModel())
       .register(meterRegistry).increment();

return doRelay(...)
    .doOnNext(chunk -> { if (first.getAndSet(false)) ttftTimer.record(...); })
    .doFinally(sig -> {
        sample.stop(Timer.builder("gateway.total")
            .tag("channel", channel.name())
            .tag("result", sig == SignalType.ON_COMPLETE ? "ok" : "cancel")
            .register(meterRegistry));
        inflight.decrement();
    });
```

**高基数警告**：`request_id`、`user_id` 绝对不能做 tag（会撑爆 Prometheus）。租户维度用采样或只进日志。

## 2. 日志规范

### 2.1 三类日志

| 类型 | 级别 | 内容 | 去向 |
|---|---|---|---|
| 访问日志 | INFO | requestId、tenant、key前缀、模型、渠道、状态、耗时、token、成本 | 文件 → Loki/ES |
| 错误日志 | ERROR | 异常栈、上游响应片段（截断 2KB）、route_trace | 文件 → 告警 |
| 审计日志 | INFO | 谁在何时改了哪个配置（前后值 diff） | MySQL `audit_log` |

### 2.3 脱敏规则

- `authorization` / `x-api-key` / `x-goog-api-key` → `***`
- 请求体默认不记录；开启 `log.payload=true` 时：
  - 文本内容截断至 1KB
  - 图片 base64 替换为 `[image:image/png:12KB]`
  - 命中 PII 正则（手机号、身份证、银行卡）时掩码
- 上游错误响应截断 2KB 并去除可能的密钥回显

## 3. 链路追踪

- 使用 Micrometer Tracing + OTLP（或 Zipkin）。
- Span 划分：
  ```
  http.server (客户端请求)
   ├─ auth.verify
   ├─ route.resolve
   ├─ quota.reserve
   ├─ http.client (上游调用)
   └─ usage.publish (异步，独立 trace)
  ```
- 上游 W3C `traceparent` 透传（若渠道开启），便于与厂商联调。
- 采样率：默认 1%，错误请求 100% 采样（tail-based 需 collector 支持）。

## 5. 告警规则（Prometheus）

```yaml
groups:
- name: gateway
  rules:
  - alert: HighErrorRate
    expr: sum(rate(gateway_errors_total[5m])) / sum(rate(gateway_requests_total[5m])) > 0.05
    for: 3m
    labels: { severity: critical }
    annotations: { summary: "网关错误率 > 5%" }

  - alert: HighAddedLatency
    expr: histogram_quantile(0.99, sum(rate(gateway_added_latency_bucket[5m])) by (le)) > 0.010
    for: 5m
    labels: { severity: warning }

  - alert: ChannelBreakerOpen
    expr: gateway_breaker_state == 2
    for: 1m
    labels: { severity: critical }
    annotations: { summary: "渠道 {{ $labels.channel }} 熔断" }

  - alert: UsageDlqGrowing
    expr: increase(gateway_usage_dlq_size[10m]) > 100
    labels: { severity: critical }

  - alert: QuotaReserveSlow
    expr: histogram_quantile(0.99, sum(rate(gateway_quota_reserve_seconds_bucket[5m])) by (le)) > 0.005
    for: 5m
    labels: { severity: warning }
```

## 6. 容量规划

### 6.1 单实例能力（4C8G 估算，需实测校正）

| 场景 | 并发 SSE | QPS（短请求） | 说明 |
|---|---|---|---|
| 透传 | 3000~5000 | 2000+ | 瓶颈在连接数与带宽 |
| 翻译 | 1500~2500 | 800 | 瓶颈在 JSON 编解码 CPU |
| 混合 7:3 | ~2500 | ~1500 | — |

### 6.2 扩容信号

- `gateway_inflight / maxConcurrentStreams > 0.7` 持续 10min → 加副本
- CPU > 70% 持续 10min → 加副本
- Redis 命令延迟 P99 > 5ms → 拆分 Redis（配额与缓存分离）

### 6.3 关键 JVM 参数

```bash
java -Xms4g -Xmx4g \
     -XX:+UseZGC -XX:ZCollectionInterval=5 \
     -XX:MaxDirectMemorySize=1g \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/gateway \
     -Dreactor.netty.ioWorkerCount=8 \
     -Dreactor.netty.pool.maxConnections=500 \
     -Dreactor.netty.pool.acquireTimeout=5000 \
     -jar gateway-server.jar
```

> ZGC 在 8G 堆下停顿 < 1ms，适合长连接低延迟场景；若 JDK 17 默认 G1，需显式开启 ZGC（JDK 17 支持，生产可用）。

### 6.4 连接数与文件句柄

```
单实例 1000 并发 SSE：
  客户端连接 1000 + 上游连接 1000 = 2000 socket
  ulimit -n 建议 65535
  net.ipv4.tcp_tw_reuse = 1
  net.core.somaxconn = 4096
```

## 7. 发布与回滚

### 7.1 优雅下线

```java
@Component
public class GracefulShutdown implements ApplicationListener<ContextClosedEvent> {
    public void onApplicationEvent(ContextClosedEvent e) {
        // 1. 就绪探针立即返回 503（LB 摘除）
        readiness.setReady(false);
        // 2. 停止接收新请求，等待在途请求完成（最长 120s）
        awaitInflight(Duration.ofSeconds(120));
        // 3. 关闭连接池
    }
}
```

- K8s：`preStop: sleep 10` + `terminationGracePeriodSeconds: 150`。
- Nginx：先 `down` 再 `reload`。

### 7.2 回滚

- 镜像版本回退（保留最近 5 个 tag）。
- 数据库迁移使用 Flyway，**只做向前兼容变更**（加列不删列，两个版本后清理）。
- 配置回滚：`route_table` 保留最近 20 个版本快照，一键恢复。

## 8. 成本控制（运维视角）

| 手段 | 效果 |
|---|---|
| 亲和提高 prompt cache 命中 | 缓存读价格通常是输入的 1/10 |
| 分级定价正确配置 | 长上下文请求避免被低价档误算 |
| 低价渠道优先（priority） | 国产模型成本可降至 1/10 |
| `max_tokens` 上限约束 | 防止单请求失控 |
| 租户日额度 | 防止 Key 泄漏导致巨额账单 |
| 异常检测（单 Key 突增 10 倍） | 及时发现盗刷 |

## 9. 常见故障速查

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 客户端收到 200 但无内容 | 未 flush / 中间层缓冲 | 检查 Nginx `proxy_buffering off`；抓包看首帧时间 |
| 流式中途断开 | 上游空闲超时 / LB 60s 超时 | 加心跳；调 `proxy_read_timeout` |
| 全部请求 503 | 候选集为空 / Redis 挂了且 fail-closed | 看 `gateway_breaker_state`、Redis 连通性 |
| 计费为 0 | usage 未解析到 | 看 `usage_source`；抓上游尾帧 |
| 余额不降 | 结算未触发 | 看 `quota_reservation` 状态；查消费者是否堆积 |
| 偶发 401 | 多 Key 中某个失效 | 看 `channel_key.status`；熔断日志 |
| P99 突然升高 | 某渠道慢但未熔断 | 看渠道 TTFT 分位；考虑按延迟熔断（P2） |
| 内存持续上涨 | 请求体未释放 / 连接泄漏 | 堆 dump；看 `direct_memory` 与 `inflight` |
