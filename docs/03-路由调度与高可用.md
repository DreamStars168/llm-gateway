# 03 路由、调度与高可用设计

> 目标：在多渠道、多 Key、多上游质量参差的现实下，做到"请求有处可去、失败快速绕开、同一会话不抖"。

---

## 1. 领域模型

```
Tenant 1 ── n ApiKey
Tenant 1 ── n Group ── n Channel          （Group 是权限与计费边界）
VirtualModel 1 ── n ModelRoute ── 1 Channel
Channel 1 ── n ChannelKey（同渠道多账号轮换）
VirtualModel 1 ── n ModelAlias            （别名归一）
```

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `virtual_model` | `name`、`display_name`、`context_window`、`capabilities`(json)、`status` | 对客户端暴露的模型名，如 `gpt-4o`、`claude-sonnet-4` |
| `model_alias` | `alias`、`virtual_model_id`、`match_type`(exact/prefix/regex) | `claude-opus-4-7-20260101` → `claude-opus-4` |
| `channel` | `name`、`provider`、`protocol`、`base_url`、`group_id`、`priority`、`weight`、`max_inflight`、`timeout_ms`、`passthrough` | 一个上游接入点 |
| `model_route` | `virtual_model_id`、`channel_id`、`upstream_model`、`priority`、`weight`、`enabled`、`context_window`、`price_ratio` | 虚拟模型到真实模型的映射，粒度到此才能真正控成本 |
| `channel_key` | `channel_id`、`cipher`、`key_version`、`status`、`weight`、`last_error`、`cooldown_until` | 同渠道多账号（多 Key 轮换） |
| `route_policy` | `scope`、`strategy`、`sticky_ttl`、`retry_max`、`failover_on`(json) | 策略可绑 group / virtual_model |

> 关键设计：**路由挂在 `model_route` 而不是 `channel`**。同一渠道可以给不同虚拟模型映射不同上游模型名和不同倍率；同一虚拟模型可以挂多个渠道形成候选集。这是 new-api / sub2api 的 channel→model 多对多思路，比 one-api 的单 channel 单模型更灵活。

## 2. 四级决策流水线

```
请求(virtualModel, groupId, sessionKey)
   │
   ├─① 候选集构建：group 内 + model_route.enabled + 渠道启用 + 协议兼容
   │                 → List<Candidate{route, channel, key}>
   │
   ├─② 亲和命中：sessionKey → sticky 映射 → 若候选仍在且健康，直接返回
   │
   ├─③ 优先级分层：按 route.priority 升序分组，只在最高优先级层内做加权
   │                 （优先级是"硬分层"，权重是"层内软分配"）
   │
   ├─④ 加权选择 + 健康过滤：
   │      过滤：熔断打开 / 冷却中 / 并发闸门满 / Key 失效
   │      选择：smooth weighted round-robin（平滑加权轮询，避免突发）
   │
   └─▶ SelectedCandidate（含备选队列，用于失败转移）
```

### 2.1 平滑加权轮询（SWRR）

Nginx 的经典算法，避免"权重 5:1 时前 5 个请求全打 A"的突发：

```java
// 每次选择：current += weight; 选 current 最大者; 选中者 current -= totalWeight
record Node(int weight, AtomicInteger current) {}
```

- 状态存本地（每实例独立），无需 Redis，天然分摊。
- 缺点：多实例间不均衡 → 大流量下趋近均衡，小流量下有偏斜，可接受。
- 备选：`random weighted`（实现更简单，分布方差略大）；配置项 `strategy=RANDOM_WEIGHTED` 可切换。

### 2.2 会话亲和（Sticky）

| 客户端 | 会话标识来源（按优先级） |
|---|---|
| Claude Code | 请求头 `x-claude-code-session-id` → `metadata.user_id` |
| Codex | `prompt_cache_key` → 请求头 `session_id` |
| OpenAI Chat | 请求体 `user` → 请求头 `x-session-id` → 首条 user 消息的 SHA-256 前 16 位 |
| Gemini | 请求头 `x-session-id` → 首条 user 内容 hash |

```
Redis: sticky:{groupId}:{virtualModel}:{sessionHash}  →  {channelId}:{keyId}   TTL 30min
```

- 命中条件：候选仍存在、渠道未熔断、Key 未冷却。否则重新选择并**覆盖**映射（不保留坏映射）。
- TTL 续期：每次命中 `EXPIRE` 重置为 30min（滑动窗口）。
- 亲和的价值：**保住上游 prompt cache**。跨账号缓存独立，乱切会显著增加成本 —— 这是 cc-router 明确强调的点，也是简历里"会话亲和"的真实动机，面试要能讲清楚。

### 2.3 亲和 vs 负载均衡的取舍

| 策略 | 适用 | 代价 |
|---|---|---|
| `PRIORITY`（顺序） | 小额套餐先用完 A 再用 B；命中缓存最好 | 峰值时 A 限流才切 B，有抖动 |
| `WEIGHTED`（加权轮询） | 多账号均衡分摊 | 缓存命中率下降，成本上升 |
| `STICKY`（会话亲和） | 多账号 + 在意缓存 | 实现复杂，需 Redis |
| `LEAST_LATENCY`（P2） | 上游质量差异大 | 需 EWMA 统计，冷启动偏差 |

默认：`STICKY`，`sticky_ttl=30m`，`retry_max=2`。

## 3. 熔断设计

### 3.1 粒度

**`channel × upstream_model`** 维度。理由：某渠道的 `gpt-4o` 限流不代表 `gpt-4o-mini` 不可用；整渠道熔断会造成误伤。

### 3.2 状态机

```
                失败率≥50% 且 窗口内≥20 次
   CLOSED ────────────────────────────────▶ OPEN
     ▲                                        │
     │  连续 5 次探测成功                       │ 冷却 30s
     │                                        ▼
     └────────────────────────────────── HALF_OPEN
                            （放行 3 个探测请求）
```

- 滑动窗口：本地 `RingBuffer`，10s 窗口，桶宽 1s。
- 统计口径：连接失败、5xx、429（单独计数，权重更高）、首字节超时算失败；4xx（400/401/403）**不算**渠道失败（是请求或凭证问题，走别的处理）。
- 状态共享：本地为主（快），变更时异步广播到 Redis `breaker:{channelId}:{model}` 供其他节点参考（最终一致，允许短暂不一致）。

### 3.3 冷却与退避

| 失败类型 | 冷却 | 说明 |
|---|---|---|
| 429 | `Retry-After` 头优先，否则 30s | 尊重上游 |
| 5xx | 15s | 快速恢复 |
| 连接失败 | 10s | 网络抖动 |
| 401/403 | 300s 且标记 Key 失效 | 需人工介入，避免刷爆 |
| 连续 3 次熔断 | 冷却翻倍（上限 10min） | 指数退避 |

## 4. 重试与故障转移

### 4.1 可重试判定矩阵

| 阶段 | 错误 | 是否换渠道 | 说明 |
|---|---|---|---|
| 建连前 | 无候选 | 否 | 直接 503 |
| 建连 | ConnectException / DNS | 是 | 换渠道 |
| 发送后未响应 | 首字节超时（默认 60s，可配） | 是 | 仅当客户端未收到任何字节 |
| 响应 429 | RateLimit | 是 | 优先换 Key，再换渠道 |
| 响应 5xx / 529 | ServerError | 是 | — |
| 响应 400 / 422 | 请求非法 | 否 | 换渠道也一样错 |
| 响应 401 / 403 | 凭证/权限 | 是（换 Key）+ 标记失效 | 同渠道其他 Key 可试 |
| 已写出首字节 | 任何错误 | **否** | 只能发 error 事件终止 |

### 4.2 重试策略

```java
record RetryPolicy(
    int maxAttempts,            // 默认 2（即最多 3 个候选）
    Duration perAttemptTimeout, // 默认 60s（首字节）
    Set<String> retryOn,        // 见上表
    boolean retryOtherKeyFirst  // 429/401 时先换同渠道的其他 Key
) {}
```

- **只在"未向客户端写出任何字节"时重试**，这是硬约束，否则会拼接出脏流。
- 重试需重新走一遍「配额预扣」吗？不需要：预扣按 `requestId` 幂等，重试沿用同一 `reservationId`，仅当渠道切换导致价格不同（`price_ratio`）时在结算阶段修正。
- 每次尝试记一条 `relay_attempt`，便于排查"到底打了几家"。

### 4.3 超时分层

| 超时 | 默认 | 作用 |
|---|---|---|
| 客户端读超时（LB） | 600s | 长响应兜底 |
| 上游首字节超时 | 60s | 判死换渠道 |
| 上游空闲超时 | 120s | 流中途无数据 → 发心跳或终止 |
| 上游总时长 | 600s | 防僵尸连接 |
| 配额预扣 Redis 超时 | 300ms | 超时降级（见 04 文档） |

## 5. 并发与限流

### 5.1 四层限流

| 层 | Key | 算法 | 目的 |
|---|---|---|---|
| 全局入站 | 实例 | 信号量 8000 | 自我保护，OOM 前拒绝 |
| 租户 RPM/TPM | `tenant:{id}:{minute}` | Redis 固定窗口 | 商业套餐限速 |
| API Key | `key:{id}:{minute}` | Redis 滑动窗口（ZSET） | 精细限速 |
| 渠道并发 | 本地 `Semaphore(maxInflight)` | 直接计数 | 保护上游 |

### 5.2 令牌桶 vs 滑动窗口

- **RPM（请求数）**：Redis ZSET 滑动窗口，精确但内存开销大（每请求一个 member）。用 `ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` 三段 Lua 原子化。Key 数量可控时可行。
- **TPM（token 数）**：无法预知本次消耗 → 采用「预扣估算 + 结算修正」：按 `max_tokens` 或历史均值预扣，响应后修正。这与配额扣减同构，复用同一套 Lua。
- 单机场景可退化为 Caffeine + 令牌桶，减少 Redis 往返。

### 5.3 并发闸门实现要点

```java
Semaphore gate = channelGates.get(channelId);
if (!gate.tryAcquire()) { return FilterReason.INFLIGHT_FULL; }   // 不阻塞，直接换候选
try { ... } finally { gate.release(); }
```

必须 `finally` 释放，且流式场景要在 `doFinally` 释放（不能只在 `onComplete`，客户端取消也要释放）。

## 6. 渠道健康与探测

| 机制 | 频率 | 行为 |
|---|---|---|
| 被动统计 | 每请求 | 更新 SWRR 健康分、熔断窗口 |
| 主动探活 | 60s（仅对 `OPEN`/可疑渠道） | 发最小请求（`max_tokens=1`），成功则半开 |
| 余额查询 | 5min（支持的厂商） | 更新 `channel.balance`，低于阈值告警 |
| 模型列表同步 | 手动/每日 | 拉取 `/v1/models` 更新 `model_route` 候选提示 |
| 凭证过期检查 | 启动 + 每小时 | OAuth 类渠道刷新 token |

> 主动探测会产生费用，默认只探测熔断中的渠道，且用最便宜的模型。

## 7. 配置热更新

```
Admin API 写入 MySQL ─▶ 版本号 +1 ─▶ Redis PUBLISH cfg:invalidate {version}
                                              │
         ┌────────────────────────────────────┼────────────────────────────┐
         ▼                                    ▼                            ▼
   gateway-1 收到 ── 异步拉取快照 ──▶ 构建新 RouteTable ──▶ AtomicReference.set()
   gateway-2 ...（同上）
```

- 快照结构：`{version, channels[], routes[], virtualModels[], aliases[], policies[]}`，一次性拉全量（万级记录 < 2MB，够用）。
- 本地 `AtomicReference<RouteTable>`，读路径无锁。
- 兜底：每 60s 轮询版本号，防止 Redis Pub/Sub 丢消息。
- **不允许**在数据面回调管理端接口，避免控制面故障拖垮数据面。

## 8. 灰度与降级

| 场景 | 降级动作 |
|---|---|
| Redis 不可用 | 配额按租户配置 `fail-open`（放行 + 记账）或 `fail-closed`（503）；亲和失效 → 退化为 SWRR；限流退化为本地令牌桶 |
| RabbitMQ 不可用 | 用量写本地 `usage_outbox`（追加文件/内存队列），恢复后补发 |
| MySQL 不可用 | 数据面不受影响（不依赖）；管理端只读降级 |
| 某渠道全挂 | 熔断自动摘除，候选集为空则返回 503 并提示可用模型 |
| 上游大面积 429 | 触发全局告警 + 自动降低该渠道权重至 0（临时） |

灰度能力：
- 渠道级 `canary_weight`（新渠道先给 5% 流量）。
- 模型级 `enabled_for_groups`（先对内部租户开放新模型）。

## 9. 路由可观测性

每条请求记录 `RouteDecision`：

```json
{
  "request_id": "req_01HX...",
  "virtual_model": "claude-sonnet-4",
  "candidates": 4,
  "filtered": [{"channel": "ch-b", "reason": "BREAKER_OPEN"}, {"channel": "ch-c", "reason": "INFLIGHT_FULL"}],
  "sticky_hit": true,
  "selected": {"channel": "ch-a", "key": "key-2", "upstream_model": "claude-sonnet-4-20250514"},
  "attempts": [{"channel": "ch-a", "status": 429, "ms": 320}, {"channel": "ch-d", "status": 200, "ms": 1180}],
  "strategy": "STICKY",
  "table_version": 142
}
```

- 落 `relay_log`（异步），管理端"路由追踪"页可按 requestId 回放完整决策链。
- 指标：`gateway_route_total{strategy,result}`、`gateway_failover_total{from,to,reason}`、`gateway_breaker_state{channel,model}`。

## 10. 关键场景推演（面试常问）

**Q：两个渠道，A 额度小但缓存命中高，B 额度大但贵，怎么配？**
A：`priority` 设 A=1、B=2，策略 `STICKY`。正常流量落在 A 并保缓存；A 返回 429 时熔断 30s，期间流量走 B；A 冷却后半开探测，恢复则回切。这样"省钱优先，不断流兜底"。

**Q：1000 并发下某渠道突然全 500，会发生什么？**
A：前 20 个失败请求触发熔断（10s 窗口失败率 100% > 50%），该 `channel×model` 标记 OPEN，后续请求在候选集构建阶段被过滤，直接走备份渠道；同时异步广播到其他节点。整个过程无请求排队，P99 不受影响（除了那 20 个触发请求各多花一次重试）。

**Q：客户端断开了，上游还在生成，怎么办？**
A：WebFlux 的 `doFinally(CANCEL)` 触发 → `Disposable.dispose()` 关闭上游连接 → 上游停止计费；同时按已收到的 chunk 结算实际用量（含 `estimated=true` 标记）。

**Q：怎么保证同一会话不乱切导致 prompt cache 失效？**
A：`sticky` 映射 + 30min 滑动 TTL；只有候选不健康时才覆盖映射，且覆盖后记录 `sticky_rebind` 指标，便于观察抖动率。目标：`sticky_rebind_rate < 1%`。
