## 一、指标体系

### 1.1 四大黄金信号

| 信号 | 指标 | 告警阈值 |
|---|---|---|
| 流量 | `gateway_requests_total{protocol_in,model,channel}` | 突降 50% / 突增 300% |
| 错误 | `gateway_errors_total{code,channel}` | > 5% 持续 3min |
| 延迟 | `gateway_added_latency`、`gateway_ttft_seconds` | 附加延迟 P99 > 10ms |
| 饱和度 | `gateway_inflight`、`channel_inflight` | 闸门 > 80% 持续 5min |

### 1.2 业务指标

| 指标 | 说明 |
|---|---|
| `gateway_tokens_total{type=input\|output\|cached\|reasoning}` | 按模型/渠道/租户 |
| `gateway_cost_micro_total` | 成本（micro-USD） |
| `gateway_failovers_total{from,to,reason}` | 故障转移次数 |
| `gateway_breaker_state{channel,model}` | 0=CLOSED 1=HALF_OPEN 2=OPEN |
| `gateway_sticky_hit_total` | 亲和命中次数 |
| `gateway_dynamic_weight{channel,model}` | 当前生效权重 |
| `gateway_quota_reserve_seconds` | 预扣耗时 |

> **高基数警告**：`request_id`、`user_id` 绝不能做 tag，会撑爆 Prometheus。

### 1.3 埋点位置

```java
Timer.Sample sample = Timer.start(meterRegistry);
Counter.builder("gateway.requests")
       .tag("protocol_in", ctx.protocol().name())
       .tag("model", req.virtualModel())
       .register(meterRegistry).increment();

return doRelay(...)
    .doOnNext(chunk -> { if (first.getAndSet(false)) ttftTimer.record(...); })
    .doFinally(sig -> {
        sample.stop(Timer.builder("gateway.total")
            .tag("channel", channel.name())
            .tag("result", sig == SignalType.ON_COMPLETE ? "ok" : "cancel")
            .register(meterRegistry));
    });
```

## 二、日志

### 2.1 三类日志

| 类型 | 级别 | 内容 | 去向 |
|---|---|---|---|
| 访问日志 | INFO | requestId、tenant、模型、渠道、状态、耗时、token、成本 | 文件 → Loki |
| 错误日志 | ERROR | 异常栈、上游响应片段（截断 2KB）、route_trace | 文件 → 告警 |
| 审计日志 | INFO | 谁在何时改了哪个配置（前后值 diff） | MySQL `audit_log` |

### 2.3 脱敏规则

- `authorization` / `x-api-key` / `x-goog-api-key` → `***`
- 请求体默认不记录；开启时文本截断 1KB、图片 base64 替换为 `[image:image/png:12KB]`
- 上游错误响应截断 2KB 并去除可能的密钥回显

## 三、告警规则

```yaml
groups:
- name: gateway
  rules:
  - alert: HighErrorRate
    expr: sum(rate(gateway_errors_total[5m])) / sum(rate(gateway_requests_total[5m])) > 0.05
    for: 3m
    labels: { severity: critical }

  - alert: HighAddedLatency
    expr: histogram_quantile(0.99, sum(rate(gateway_added_latency_bucket[5m])) by (le)) > 0.010
    for: 5m
    labels: { severity: warning }

  - alert: ChannelBreakerOpen
    expr: gateway_breaker_state == 2
    for: 1m
    labels: { severity: critical }

  - alert: UsageDlqGrowing
    expr: increase(gateway_usage_dlq_size[10m]) > 100
    labels: { severity: critical }
```

## 四、压测

### 4.1 环境与方法

| 项 | 配置 |
|---|---|
| 网关 | 单机，JDK 17 |
| Mock 上游 | 同机，首字节 ~200ms，每帧 40ms，共 40 帧（单请求约 750ms） |
| 依赖 | Redis 7 / MySQL 8 / RabbitMQ 3.13（Docker，同机） |
| 工具 | `scripts/load-test.mjs`（Node.js，keep-alive + 流式读取） |

**附加延迟测量方法**：同一并发下分别压「直连上游」与「经网关」，比较 TTFT。
上游处理时间被抵消，差值即网关附加延迟。两轮之间强制间隔 3s，避免上游积压污染。

### 4.2 吞吐与稳定性

| 场景 | 并发 | 总请求 | 失败 | 吞吐 | 相对直连 |
|---|---|---|---|---|---|
| 直连 Mock 上游（基线） | 200 | 4121 | 0 | 261.9 req/s | 100% |
| **经网关（最终版）** | 200 | **7634** | **0** | **248.3 req/s** | **94.8%** |

**结论**：200 并发零错误，吞吐达直连的 94.8%，网关开销仅 5.2%。

### 4.3 网关附加延迟

**并发 20，各 400 样本**：

| 路径 | P50 | P95 | P99 |
|---|---|---|---|
| 直连上游 | 1.7 ms | 18.4 ms | 21.3 ms |
| 经网关 | 4.1 ms | 24.3 ms | 26.4 ms |
| **附加延迟** | **2.4 ms** | **5.9 ms** | **5.1 ms** |

**复测（各 300 样本）**：

| 并发 | P50 | P95 | P99 |
|---|---|---|---|
| 20 | **1.6 ms** | 2.8 ms | **2.2 ms** |
| 50 | 6.9 ms | 20.4 ms | 19.1 ms |

**结论**：并发 20 时 P50 1.6~2.4ms、P99 2.2~5.1ms，**满足 < 10ms 目标**。
50 并发时 P99 升至 19.1ms（Redis 单连接排队，见瓶颈分析）。

### 4.4 瓶颈分析

**已定位**：Lettuce reactive 模式默认**单连接多路复用**，
`spring.data.redis.lettuce.pool` 对 `ReactiveStringRedisTemplate` 不生效。

实测证据：
- 网关到 Redis 仅 **1 条 TCP 连接**
- Redis 服务端能力：5000 次 Lua 原子预扣仅 193ms（≈26000 次/秒）
- 因此高并发下的 P99 升高来自**客户端侧排队**，不是 Redis 慢

**优化方向**：

| 方案 | 预期收益 | 状态 |
|---|---|---|
| 调大 Redis timeout + FAIL_OPEN 降级 | 消除超时 500 | ✅ 已实施 |
| 租约预取（batch reserve） | P99 35ms → 5ms | ⚠️ 已回退（见下） |
| 余额拆 available/frozen 子账户 | 租约的正确实现 | 后续工作 |
| 非 reactive 模板 + 连接池 | 提升预扣并发 | 需阻塞线程池，有 event loop 风险 |

**租约方案的失败复盘**：

做法：一次向 Redis 预扣 N 份额度缓存在本地，后续本地扣减，耗尽时续租。

- 结果：附加延迟 P99 从 35.7ms 降到 5.1ms（改善明显）
- **但账目不平**：租约剩余额度无法在正确时机核销，巡检归还时又重复扣款，
  实测 25 次请求后 balance 多扣 160 micro

**决策：回退**。这是一个管钱的系统，账目正确性优先于 5ms 延迟。
正确实现需要把余额拆成 `available` / `frozen` 两个子账户 + 定时对账，复杂度显著上升。

### 4.5 压测暴露并修复的缺陷

| # | 问题 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | Redis 命令超时 | 200 并发下 25~35 个 500 | 300ms timeout 被高并发击穿 | 调至 500ms + 连接池 |
| 2 | 配额故障拖垮请求 | Redis 抖动直接影响成功率 | 无降级路径 | FAIL_OPEN 放行 + 后补结算 |
| 3 | Lettuce 池缺依赖 | 启动失败 `ClassNotFoundException` | 未引入 `commons-pool2` | 添加依赖 |
| 4 | 非流式计费为 0 | 转换后响应解析不到 usage | 只认 OpenAI 字段，不认 Anthropic | 支持三种格式 |
| 5 | 租约导致账目不平 | balance 与 reserved 对不上 | 核销时机冲突 | 回退到按请求预扣 |

> 第 1、2、5 条只在真实压测/长跑中暴露，单元测试覆盖不到。

## 五、容量规划

### 5.1 单实例能力（实测校正）

| 场景 | 并发 | 吞吐 | 说明 |
|---|---|---|---|
| 透传 | 200 零错误 | 248 req/s | 当前实测上限 |
| 50 并发 | P99 19ms | — | Redis 单连接排队 |

### 5.2 扩容信号

- `gateway_inflight / maxConcurrentStreams > 0.7` 持续 10min → 加副本
- CPU > 70% 持续 10min → 加副本
- Redis 命令延迟 P99 > 5ms → 拆分 Redis（配额与缓存分离）

### 5.3 JVM 参数

```bash
java -Xms4g -Xmx4g \
     -XX:+UseZGC -XX:ZCollectionInterval=5 \
     -XX:MaxDirectMemorySize=1g \
     -XX:+HeapDumpOnOutOfMemoryError \
     -Dreactor.netty.ioWorkerCount=8 \
     -jar gateway-server.jar
```

ZGC 在 8G 堆下停顿 < 1ms，适合长连接低延迟场景。

### 5.4 系统参数

```
ulimit -n 65535              # 单实例 200 并发 ≈ 400 socket
net.ipv4.tcp_tw_reuse = 1
net.core.somaxconn = 4096
```

## 六、故障速查

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 客户端收到 200 但无内容 | 未 flush / 中间层缓冲 | 检查 Nginx `proxy_buffering off` |
| 流式中途断开 | 上游空闲超时 / LB 60s 超时 | 加心跳；调 `proxy_read_timeout` |
| 全部请求 503 | 候选集为空 / Redis 挂了且 fail-closed | 看 `gateway_breaker_state` |
| 计费为 0 | usage 未解析到 | 看 `usage_source`；抓上游尾帧 |
| 余额不降 | 结算未触发 | 看 `quota_reservation` 状态；查消费者堆积 |
| 偶发 401 | 多 Key 中某个失效 | 看 `channel_key.status` |
| P99 突然升高 | 某渠道慢但未熔断 | 看渠道 TTFT 分位 |
| 内存持续上涨 | 请求体未释放 / 连接泄漏 | 堆 dump；看 `direct_memory` 与 `inflight` |

## 七、复现命令

```bash
# 依赖
docker compose up -d redis mysql rabbitmq mock-primary mock-backup

# 初始化余额
redis-cli SET quota:1:balance 9999999999
redis-cli SET quota:1:reserved 0

# 压测
node scripts/load-test.mjs --concurrency 200 --duration 30

# 附加延迟（必须分开跑，否则第二轮被第一轮污染）
node scripts/measure-overhead.mjs --mode direct  --concurrency 20 --samples 400
node scripts/measure-overhead.mjs --mode gateway --concurrency 20 --samples 400
```
