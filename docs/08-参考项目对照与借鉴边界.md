# 08 参考项目对照与借鉴边界

> 原则：**借鉴架构与协议细节，不复制代码**。五个参考项目许可证不同（AGPL-3.0 / LGPL-3.0 / MIT / 商业双授权），直接拷贝源码会给简历项目带来法务与"抄袭"双重风险。

## 3. 逐项目可借鉴点（只学设计）

### 3.1 cc-router（MIT，最值得精读）

**可借鉴**
1. **虚拟模型槽位**：把 `opus/sonnet/haiku` 抽象成虚拟模型，同一虚拟模型绑多个真实模型；客户端不用改配置就能换上游 —— 这是"聚合"的本质。
2. **别名模糊匹配**：`claude-opus*` 前缀匹配，兼容各家 SDK 硬编码的模型名。设计成 `model_alias.match_type = exact | prefix | regex`。
3. **调度三模式**：顺序 / 轮询 / 会话亲和，并明确写出各自适用场景（顺序=榨干小额套餐且缓存好；亲和=均衡且不丢缓存）。这套取舍论证可以直接用在你的设计文档里。
4. **会话标识提取顺序**：`x-claude-code-session-id` → `metadata.user_id`；Codex 用 `prompt_cache_key` → `session_id`。这是实战踩出来的，照抄这个优先级即可。
5. **入口/出口双协议矩阵 + "有原生端点就优先走原生"** 的明确主张。
6. **透传客户端请求头开关**（`anthropic-beta` 白名单），按渠道粒度控制。

**不要学**
- Tauri 桌面端的本地 HTTPS 自签证书、OAuth 订阅账号（ChatGPT/Kiro 登录）—— 灰色地带，不要碰。
- 单机 SQLite + 本地文件配置（不适合服务端多租户）。

### 3.2 new-api（AGPL-3.0，架构参考价值最高）

**可借鉴**
1. **分层**：`router / middleware / controller / relay / service / model`，`relay` 里再分 `channel`（上游适配）与 `adaptor`（协议转换）。你的包结构可以对应：`admin(controller) / routing / relay / protocol / billing`。
2. **RelayKit 独立模块**：把"协议 DTO + 转换"抽成独立可编译单元，不依赖主工程。**这一点强烈建议照做**（你的 `protocol/` 包应零依赖 Spring），好处是可单测、可复用、可开源。
3. **四协议互转矩阵**：README 明确写了 Chat / Responses / Messages / Gemini 之间的转换支持度，并声明"协议特定工具与字段可能无法精确映射"。这种"诚实地列出不支持项"的做法要学。
4. **渠道亲和（channel affinity）**：在优先级+权重之外提供"同渠道粘性"，与你的 sticky 一致。
5. **表达式定价**：用表达式描述阶梯价，比硬编码 if-else 灵活。你可以简化为"档位 + 倍率"。
6. **任务插件 API**：`/v1/tasks/{pluginKey}` 异步任务模式，第二期做图片/视频时可直接套用。

**不要学**
- Go 的 Gin 生态与你的 Java 栈不同；不要照搬代码结构细节。
- AGPL 代码不能拷进你的项目（尤其如果你以后想闭源或商用）。

### 3.3 sub2api（LGPL-3.0）

**可借鉴**
1. **分层限流**：用户级 + 账号级并发、请求速率、token 速率四类限制，且明确"流式请求的并发槽在 turn 之间释放"（WebSocket 场景）。你的四层限流可对齐。
2. **账号状态机**：`401 → 临时摘除`、`403 → 权限失败不重试`、`429 → 按 Retry-After 冷却`。这套判定表可以直接映射到你的"重试判定矩阵"。
3. **复合分组（Composite Groups）**：管理员路由层把"请求的模型"解析到"具体 provider"，支持多 provider 分组。这与你 `virtual_model → model_route → channel` 是同一思想，可互相印证。
4. **配置安全**：`url_allowlist`（防 SSRF）、`trusted_proxies`（防伪造 XFF）、`response_header` 过滤、`csp`。这些是生产必做项，成本低但容易被忽略。
5. **渐进式简单模式**：`RUN_MODE=simple` 隐藏 SaaS 功能，适合个人/内网。你可以做 `gateway.mode=simple|full`。

**不要学**
- 内置支付（EasyPay/Stripe）、拼车共享等运营功能，与简历项目无关且增加合规负担。
- PostgreSQL + Ent 的 ORM 选型（你已定 MySQL + MyBatis-Plus）。

### 3.4 fizz-gateway-node（AGPL-3.0，企业网关视角）

**可借鉴**
1. **无状态节点 + 配置自动同步**：网关节点不存配置，全部从配置中心拉取，支持水平扩展。对应你的"配置快照 + AtomicReference 热替换"。
2. **插件链式拦截**：`key-auth / jwt / basic-auth` 作为插件串联在请求链上。你可以把"鉴权、限流、配额、审计"设计成 `GatewayFilter` 链（WebFilter 天然支持），保持可插拔。
3. **多级限流**：服务级 / 接口级 / APP_ID 级 / IP 级四层 —— 与你的四层限流同构，可作为论证支撑。
4. **熔断的"多种恢复策略"**：不只是固定冷却，还支持按错误类型区分恢复策略。你的冷却表已体现。
5. **性能数据**：README 给了与 Kong / Spring Cloud Gateway / ShenYu 的对比（1000 并发 12.7k QPS、P90 100ms）。你可以做类似对比表，但必须自己实测。

**不要学**
- 服务编排（HTTP/Dubbo/gRPC 热编排）、API 脱敏、水印溯源 —— 与 LLM 网关无关，是通用 API 网关的能力。
- 商业版管理后台（闭源二进制）。

### 3.5 MIXAPI（new-api 衍生）

**可借鉴**
1. **套餐计费形态**：按次套餐、包月套餐、令牌绑定套餐（限制次数/周期/频率/渠道/模型）。如果你的网关要对内收费，这是产品化参考。
2. **渠道组**：令牌选择渠道组 → 只能使用该组下渠道 + 指定模型。你的 `group` 设计已覆盖。
3. **缓存计费**：命中缓存按比例计费 —— 对应你的 `cache_read` 单独定价。
4. **运营细节**：日志清理周期、渠道 Excel 导入导出、令牌直接查余额。这些是"好用"的关键，控制台别漏。

**不要学**
- 它的很多"优化"缺乏可验证依据（README 宣称"AI 优化性能提升 50%"），不要引用这类不可复现的结论。
- 基于 new-api 的二次发行，架构上没有新增本质设计。

## 4. 你的差异化设计（简历加分项）

| 差异化点 | 说明 | 为什么五个项目都没有 |
|---|---|---|
| **双车道转发（透传/翻译自动切换）** | 同协议零拷贝透传，跨协议才走 IR；按渠道可开关 | new-api 以翻译为主；cc-router 有透传但无服务端多租户；都没有把"车道选择"作为一等设计 |
| **两阶段配额 + 幂等 reservation** | 预扣/结算/释放三态，脚本幂等 | new-api/sub2api 有配额但多为"请求后扣"或简单预扣，缺少完整的补偿与对账闭环 |
| **Playground 多模型并排 + Prompt 版本链** | 2~4 列同时流式、逐列 Abort、TTFT/成本对照、版本 diff | 五个项目均无（new-api 只有单模型试玩） |
| **路由决策可回放** | 每条请求记录候选、过滤原因、选中、重试，可视化时间线 | 各项目只有普通请求日志，无决策链 |
| **协议一致性夹具测试** | 真实录制的 SSE 样本驱动，覆盖四协议编解码 | 开源项目普遍缺协议级回归测试 |
| **可验证的性能口径** | 明确区分"网关附加延迟"与"端到端 TTFT"，压测方法可复现 | 多数项目只给模糊 QPS 数字 |

## 5. 借鉴方式（合规写法）

### 5.1 可以做

- 阅读源码理解机制，用自己的语言重写实现。
- 引用其**设计思想**并在文档中注明出处（如"会话标识提取顺序参考 cc-router"）。
- 使用其**公开 API 规范**（OpenAI/Anthropic/Gemini 的官方文档本就是公开标准）。
- 使用 MIT 项目的代码片段（cc-router），但需保留版权声明。

### 5.2 不可以做

- 复制 AGPL/LGPL 项目的代码到你的仓库（即使是"改一改"）。
- 复制其前端 UI 组件与文案。
- 在简历/答辩中声称"独立研发"却大量拷贝 —— 面试官会问细节，露馅成本极高。

### 5.3 推荐的精读顺序（按投入产出比）

1. **cc-router** `src-tauri/` 的 provider 配置与路由调度（MIT，可放心读，最贴近你的场景）
2. **new-api** `relay/` 与 `relaykit/`（看协议转换的边界处理）
3. **sub2api** `backend/internal/gateway/`（看账号状态机与并发控制）
4. **fizz-gateway-node** 的 filter/plugin 链（看企业级网关的扩展性设计）
5. **MIXAPI** 只看 README 的功能清单（产品视角）

> 建议：每个项目读完后写一份 300 字的"借鉴笔记"，答辩时能说出"我参考了 X 的 Y 机制，但做了 Z 改进"，这比空泛说"参考了开源项目"有说服力得多。
