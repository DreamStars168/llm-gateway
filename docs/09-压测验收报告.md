> 环境：Windows 11，JDK 17 (Microsoft OpenJDK 17.0.20)
> 网关：单机单实例，默认堆
> Mock 上游：同机，Anthropic 协议，首字节 ~200ms、每帧 40ms、共 40 帧（单请求约 750ms）

> 压测工具：`scripts/load-test.mjs`、`scripts/measure-overhead.mjs`（Node.js，HTTP keep-alive + 流式读取）

## 2. 网关附加延迟（核心指标）

**测量方法**：同一并发下，分别用独立进程压「直连上游」与「经网关」，比较 TTFT。
上游处理时间被抵消，差值即网关附加延迟。两轮之间强制间隔 3s，避免上游积压污染第二轮。

### 并发 20（各 400 样本）

| 路径 | P50 | P95 | P99 |
|---|---|---|---|
| 直连上游 | 1.7 ms | 18.4 ms | 21.3 ms |
| 经网关 | 4.1 ms | 24.3 ms | 26.4 ms |
| **附加延迟** | **2.4 ms** | **5.9 ms** | **5.1 ms** |

### 复测验证（各 300 样本）

| 并发 | 附加延迟 P50 | P95 | P99 |
|---|---|---|---|
| 20 | **1.6 ms** | 2.8 ms | **2.2 ms** |
| 50 | 6.9 ms | 20.4 ms | 19.1 ms |

### 结论

- **并发 20 时：P50 1.6~2.4ms，P99 2.2~5.1ms，全面达标（< 10ms）**
- 并发 50 时 P50 仍达标（6.9ms），P99 升至 19.1ms（Redis 单连接排队所致，见第 4 节）

> ⚠️ 测量注意：`measure-overhead.mjs` 早期版本在同一进程连续跑两轮，
> 第二轮受第一轮连接与上游积压影响，曾测出 1800ms 的假异常。
> 现版本已支持 `--mode direct|gateway` 分离测量，并在两轮间加 3s 间隔。

## 3. 压测暴露并修复的真实缺陷

| # | 问题 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | Redis 命令超时 | 200 并发下 25~35 个 500 | `spring.data.redis.timeout=300ms` 在高并发排队时被击穿 | 调到 500ms |
| 2 | 配额故障拖垮请求 | Redis 抖动直接影响对话成功率 | 无降级路径 | 实现 `DEGRADED` → FAIL_OPEN 放行 + 照常结算 |
| 3 | Lettuce 连接池缺依赖 | 启动失败 `ClassNotFoundException: GenericObjectPoolConfig` | 未引入 `commons-pool2` | 添加依赖 |
| 4 | `AtomicLong.increment()` 编译失败 | Maven「找不到符号」 | Java 17 下该调用在特定泛型推断上下文解析异常 | 改用 `incrementAndGet()` |
| 5 | 租约方案导致账目不平 | balance 与 reserved 对不上 | 租约剩余额度核销时机与结算冲突 | **回退到按请求预扣**（见第 5 节） |

> 第 1、2、5 条都只在真实压测/长跑中才会暴露，单元测试覆盖不到。

## 4. 瓶颈分析与后续优化

### 4.1 已定位瓶颈：Lettuce reactive 单连接

- 网关到 Redis 仅 **1 条 TCP 连接**（`connected_clients:2` 含压测客户端）。
- Lettuce 的 reactive 模式默认**单连接多路复用**，`spring.data.redis.lettuce.pool` 对 `ReactiveStringRedisTemplate` **不生效**。
- Redis 服务端能力实测：**5000 次 Lua 原子预扣仅 193ms（≈26000 次/秒）**，服务端不是瓶颈。
- 因此 50 并发时 P99 升高来自**客户端侧排队**。

### 4.2 优化方案对比（含已尝试的失败案例）

| 方案 | 预期收益 | 实测结果 | 结论 |
|---|---|---|---|
| 调大 Redis timeout | 消除超时 500 | ✅ 有效，500 归零 | **已采纳** |
| FAIL_OPEN 降级 | 配额抖动不拖垮请求 | ✅ 有效 | **已采纳** |
| 租约预取（batch reserve） | 附加延迟 P99 35ms → 5ms | ⚠️ **延迟改善但账目不平** | **已回退** |
| 非 reactive + 连接池 | 提升预扣并发 | 需阻塞线程池，有 event loop 风险 | 未实施 |
| 余额分账户（available/frozen） | 租约方案的正确实现 | — | 后续工作 |

### 4.3 租约方案失败复盘（重要经验）

**做法**：一次向 Redis 预扣 N 份额度缓存在本地，后续请求本地扣减，耗尽时续租。

**结果**：
- 附加延迟 P99 从 35.7ms 降到 **5.1ms**（改善明显）。
- 但 **balance 与 reserved 对不上账**：租约剩余额度无法在正确时机核销，巡检归还时又重复扣款，
  实测 25 次请求后 balance 多扣 160 micro。

**决策**：**回退**。理由：这是一个管钱的系统，账目正确性优先于 5ms 延迟。
租约的正确实现需要把余额拆成 `available` / `frozen` 两个子账户 + 定时对账，
复杂度显著上升，不适合在演示项目中强行落地。

> 这个"做了又回退"的过程本身就是有价值的工程判断，答辩时可以讲。

### 4.4 与简历指标的对应

简历写「单机 1000 并发 SSE、P99 附加延迟 < 10ms」。当前实测：

| 指标 | 实测 | 结论 |
|---|---|---|
| 200 并发零错误 | ✅ 7634/7634 | 达标 |
| 吞吐相对直连 | 94.8% | 优秀 |
| 附加延迟 P50（20 并发） | 1.6~2.4 ms | ✅ 达标 |
| 附加延迟 P99（20 并发） | 2.2~5.1 ms | ✅ 达标 |
| 附加延迟 P99（50 并发） | 19.1 ms | ❌ 未达标 |
| 1000 并发 | 未测 | 本机 Mock 上游在 200 并发已达上限，无法支撑 |

**建议**：简历改为「**200 并发下零错误、P99 附加延迟 < 10ms（20 并发）**」或
「单机 200 并发 SSE，网关附加延迟 P50 < 3ms」。**不要写未验证的 1000 并发**。

## 6. 复现命令

```bash
# 依赖
docker run -d --name lg-redis-dev -p 6379:6379 redis:7-alpine
docker run -d --name lg-mysql -e MYSQL_ROOT_PASSWORD=<你的密码> -e MYSQL_DATABASE=gateway -p 13306:3306 mysql:8.0
docker run -d --name lg-rabbit -e RABBITMQ_DEFAULT_USER=gateway -e RABBITMQ_DEFAULT_PASS=<你的密码> -p 5672:5672 rabbitmq:3.13-management-alpine

# 建表
docker cp db/schema.sql lg-mysql:/tmp/ && docker exec lg-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" gateway < /tmp/schema.sql'

# 启动
java -jar mock-upstream/target/mock-upstream-0.1.0-SNAPSHOT.jar --server.port=9000
MYSQL_PORT=13306 java -jar gateway-server/target/gateway-server-0.1.0-SNAPSHOT.jar

# 初始化余额（micro-USD）
redis-cli SET quota:1:balance 9999999999
redis-cli SET quota:1:reserved 0

# 压测
node scripts/load-test.mjs --concurrency 200 --duration 30

# 附加延迟（分离测量，避免污染）
node scripts/measure-overhead.mjs --mode direct  --concurrency 20 --samples 400
node scripts/measure-overhead.mjs --mode gateway --concurrency 20 --samples 400
```
