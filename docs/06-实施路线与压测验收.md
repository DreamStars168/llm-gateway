## 3. 压测方案

### 3.1 环境

| 项 | 配置 |
|---|---|
| 网关 | 4C8G，JDK 17，`-Xms4g -Xmx4g -XX:+UseZGC` |
| Redis | 2C4G，同机部署（模拟同机房） |
| MySQL | 4C8G，仅承接管理端与异步落库 |
| Mock 上游 | 4C8G，Netty，可配置固定延迟与首 token 延迟 |
| 压测机 | JMeter 5.6，与网关同网段 |

### 3.2 Mock 上游行为

```java
// mock-upstream：模拟 SSE，首 token 200ms，之后每 50ms 一帧，共 200 帧
GET /v1/messages  → 立刻返回 200 + text/event-stream
  → sleep(200ms) → 发 message_start
  → 循环 200 次：sleep(50ms) 发 content_block_delta
  → 发 message_delta(含 usage) + message_stop
```

总时长 ≈ 200ms + 200×50ms = **10.2s**，模拟真实长响应。

### 3.3 场景

| 场景 | 并发 | 时长 | 目的 |
|---|---|---|---|
| S1 基线直连 | 1000 | 5min | 测 Mock 上游本身能力 |
| S2 网关透传 | 1000 | 5min | 测网关附加延迟 |
| S3 网关翻译 | 500 | 5min | 测 IR 转换 CPU 开销 |
| S4 混合 | 1000（70% 透传 + 30% 翻译） | 10min | 贴近真实 |
| S5 故障注入 | 1000 | 5min | 主渠道 50% 请求返回 500，观察切换 |

### 3.4 关键指标采集

| 指标 | 采集方式 | 目标 |
|---|---|---|
| `gateway_added_latency` | `t_upstream_sent - t_received` | P99 < 10ms |
| `ttft_client` | 首帧写出时间 - 请求到达 | 记录基线，不设硬指标（依赖上游） |
| `qps` | Micrometer | 达到 1000 并发不降级 |
| `error_rate` | 5xx / 总请求 | < 0.1%（无故障注入时） |
| `heap_used` | JVM | 稳定，无持续增长（无泄漏） |
| `direct_memory` | `BufferPoolMXBean` | < 1GB |
| `redis_rt` | Lettuce 命令延迟 | P99 < 2ms |

### 3.5 JMeter 关键配置

```xml
<!-- 线程组 -->
<ThreadGroup>
  <stringProp name="ThreadGroup.num_threads">1000</stringProp>
  <stringProp name="ThreadGroup.ramp_time">60</stringProp>
  <boolProp name="ThreadGroup.scheduler">true</boolProp>
  <stringProp name="ThreadGroup.duration">300</stringProp>
</ThreadGroup>

<!-- HTTP 请求：必须关闭响应缓存，启用流式读取 -->
<HTTPSamplerProxy>
  <boolProp name="HTTPSampler.use_keepalive">true</boolProp>
  <stringProp name="HTTPSampler.connect_timeout">5000</stringProp>
  <stringProp name="HTTPSampler.response_timeout">60000</stringProp>
</HTTPSamplerProxy>
```

> 注意：JMeter 默认会把整个响应读进内存再统计，SSE 场景需用 `-Jjmeter.save.saveservice.response_data=false` 并只统计到首字节（用 `p90.0` 自定义断言），否则压测机先 OOM。

更推荐 **Gatling**（基于 Netty，天然支持流式）：

```scala
val scn = scenario("SSE")
  .exec(http("stream")
    .post("/v1/messages")
    .header("x-api-key", "${key}")
    .body(StringBody("""{"model":"claude-sonnet-4","stream":true,"max_tokens":256,"messages":[{"role":"user","content":"hi"}]}"""))
    .requestTimeout(60.seconds)
    .check(status.is(200)))
```

### 3.6 对比基线（写进报告）

| 方案 | 1000 并发附加延迟 P99 | 说明 |
|---|---|---|
| Spring Cloud Gateway（全量反序列化） | ~35ms | 对照，说明为何自研 |
| 本方案（透传） | < 10ms（目标 ~6ms） | — |

## 4. 并发扣减测试（M4 验收脚本）

```bash
#!/usr/bin/env bash
# 初始化：余额 100 USD，单次预扣 1 USD
redis-cli SET quota:test:balance 100000000
redis-cli SET quota:test:reserved 0

# 1000 并发，每请求 body 相同（模拟真实调用）
seq 1 1000 | xargs -P 1000 -I{} curl -s -o /dev/null -w "%{http_code}\n" \
  -X POST http://localhost:8081/v1/messages \
  -H "x-api-key: sk-lg-test" \
  -H "Content-Type: application/json" \
  -d '{"model":"claude-sonnet-4","max_tokens":256,"messages":[{"role":"user","content":"hi"}]}' \
  > result.txt

# 断言
SUCCESS=$(grep -c '^200$' result.txt)
QUOTA=$(grep -c '^402$' result.txt)
echo "success=$SUCCESS quota_exceeded=$QUOTA"
[ "$SUCCESS" -eq 100 ] && [ "$QUOTA" -eq 900 ] && echo "PASS" || echo "FAIL"
```

同时检查：
```bash
redis-cli GET quota:test:balance   # 期望 0
redis-cli GET quota:test:reserved  # 期望 0（无泄漏）
```

## 5. 故障演练清单

| # | 演练 | 预期 |
|---|---|---|
| 1 | 主渠道返回 500 | 自动切换备渠道，客户端无感知 |
| 2 | 主渠道返回 429 | 熔断 30s，期间走备渠道，恢复后半开 |
| 3 | 渠道凭证失效（401） | 标记 Key 失效，告警，切其他 Key/渠道 |
| 4 | Redis 宕机 30s | 按 `fail-open` 放行并记账，恢复后对账 |
| 5 | RabbitMQ 宕机 10min | 请求不受影响，恢复后用量补齐 |
| 6 | 客户端中途断开 | 上游连接被取消，无僵尸连接 |
| 7 | 网关滚动发布 | 长连接优雅排空，无 5xx |
| 8 | 上游卡住不返回（无首字节） | 60s 超时后换渠道 |
| 9 | 上游流中途停下（无数据 120s） | 发心跳或终止，记录部分用量 |
| 10 | 单渠道并发打满 | 闸门拒绝，自动换候选，不排队 |

## 7. 面试讲法建议（STAR）

- **S**：多模型时代，客户端协议各异（OpenAI/Anthropic/Gemini），上游渠道质量参差，直连导致改造成本高、易断流、成本不可控。
- **T**：做一个统一接入网关，要求流式零阻塞、路由可编排、计费零超卖、单机 1000 并发附加延迟 < 10ms。
- **A**：
  1. 双车道架构：原生同协议字节透传，跨协议走 IR 翻译，避免全量反序列化的性能损失。
  2. 四级路由流水线 + SWRR + Redis 会话亲和 + 渠道×模型粒度熔断，兼顾成本（缓存命中）与可用性。
  3. 两阶段配额（预扣/结算）+ 单 Lua 原子操作，解决流式场景"用量后知"导致的超卖。
  4. RabbitMQ 异步落库，把写库从请求尾延迟中剥离，幂等消费 + outbox 兜底。
- **R**：1000 并发 SSE 下附加延迟 P99 < 10ms；并发扣减测试严格 100/1000 成功；故障注入下客户端成功率 100%（自动切换）。
